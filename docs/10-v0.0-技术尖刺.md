# 10 - v0.0 技术尖刺（Walking Skeleton）

> **2026-05-21 重大修订**:首发场景由"写标书"切换为"生图原型 Agent"(见 `18-生图原型Recipe规格.md`)。本文档据此重写——尖刺目标改为 **prompt → openai-compat 中转站 → 一组 PNG**,链路更短、反馈更快、决策更便宜。原"写标书"尖刺方案保留在 git 历史,如需回退请参考 11 号文档。
>
> 在 v0.1 大规模铺架构之前,先用一个**最小、可丢弃**的尖刺验证业务链路是否成立:
> **prompt → openai-compat 中转站 → 一组 PNG → 落本地** 这条路能不能跑通、跑出来的东西能不能看。
>
> 尖刺是用来**证伪**的,不是用来留存的。代码可以丢,但**结论必须留**。
>
> 撰写日期：2026-05-20(原版) / 2026-05-21(切换到生图)

---

## 1. 为什么先做尖刺

| 不做尖刺 | 做尖刺 |
| --- | --- |
| 先搭 Electron + Core + Keychain + Trace + 打包,~3 周后才接触生图 API | **1 天**内拿到第一组真实 PNG 看效果 |
| 中转站接口不稳才发现,整套基建白做 | 接口不稳直接砍/换源,没浪费基建 |
| 错估"openai-compat 中转站"延迟与稳定性 | 早期就知道难点在哪、需要哪些 retry/超时配置 |
| 后期发现生图 API 成本爆炸 | 早期就量化 token / image / latency |

**核心要回答的 3 个问题**:

1. **质量上限**:openai-compat 中转站 + gpt-image-1(或等价模型)在常见原型描述下,产出"可用"图的比例多少?
2. **链路可行性**:Node 调中转站 → b64 解码 → 写本地 PNG → 输出 trace 这条路有没有坑?
3. **真实成本与延迟**:一次 4 张图大概多少钱、多久?能否 60s 内完成?

## 2. 范围（极度收窄）

### 2.1 做什么
| 项 | 说明 |
| --- | --- |
| 入口 | **CLI**:`moyu-spike image-gen --prompt "..." --n 4 --size 1024x1024 --out ./out/` |
| 模型 | openai-compat provider 一家(中转站),单模型(gpt-image-1 或等价) |
| 流程 | 写死的 2 步 sequence:`normalize_prompt` → `image_gen_via_relay`(fanout n 张并行) |
| 配置 | 命令行参数 + 一个 `.env` 文件存 `OPENAI_COMPAT_BASE_URL` + `OPENAI_COMPAT_API_KEY` |
| Trace | JSON 文件输出到 `./traces/<run_id>.json`(人类可读,便于复盘) |
| 产出 | N 个 `.png` 文件(`./out/<run_id>/img_<i>.png`)+ metadata.json |
| 工具栈 | Node 20 + TS + `commander` + `node-fetch` / 原生 fetch + 内置 `Buffer` |

### 2.2 不做什么（重要）
- ❌ Electron / 桌面 UI
- ❌ Keychain（API Key 直接读 `.env`）
- ❌ 自动更新 / 打包 / 多平台
- ❌ Meta-Agent / 对话造 Agent / ui.yaml 解析
- ❌ Manifest schema(流程写死在代码里)
- ❌ Sandbox(直接同进程跑;v0.1 才上 L0/L1 隔离)
- ❌ Router / 多 Provider / Fallback
- ❌ 监控 / 仪表盘 / 反馈按钮
- ❌ Memory(任何记忆)
- ❌ MCP
- ❌ 测试覆盖(写一个 happy-path E2E 即可)
- ❌ 数据库(Trace 走 JSON 文件,runs 走文件系统目录)
- ❌ ImageGrid / 项目库 / 重生成单张(v0.1+ 才上 UI)

**判断原则**:任何"不影响回答 §1 三个问题"的工作,**一律不做**。

## 4. 端到端时序

```
[CLI] node cli.ts image-gen --prompt "a minimalist desk lamp" --n 4 --size 1024x1024
   │
   ▼
[Run] 生成 run_id(UUID);trace.start()
   │
   ▼
[Step 1] normalize_prompt(prompt, style?)
   │  去空格 + 注入 style hint(如 "photorealistic, high detail")
   │  trace.step({ name, input_summary, output_summary, dur_ms })
   ▼
[Step 2] image_gen_via_relay(prompt, size, n) - fanout 并行
   │  for i in 1..n parallel:
   │    fetch(`${BASE_URL}/v1/images/generations`,
   │           { model, prompt, size, n: 1, response_format: 'b64_json' })
   │    → b64 → Buffer → fs.writeFile(out/<run_id>/img_<i>.png)
   │    trace.llm({ provider, model, dur_ms, prompt_hash })
   │    trace.artifact({ path, type: 'png', producer: 'step-2', idx: i })
   ▼
[Run] trace.end();总结打印到 stdout:
       Images: 4   Total Cost: ~$0.16   Total Time: 32s
       Files:  ./out/<run_id>/img_1.png ... img_4.png
       Trace:  ./traces/<run_id>.json
```

## 6. 必须采集的指标（写进 README 给自己看）

每跑完一批 prompt,必须记录:

| 维度 | 指标 |
| --- | --- |
| 业务 | 主观打分(1-5)每张图 / 10 张中 ≥ 3 分的比例 |
| 性能 | 总耗时(p50/p95) / 单张耗时分布 / fanout 并行效率 |
| 成本 | USD/张 / 总 USD |
| 链路 | 中转站失败率 / 超时率 / b64 解码成功率 / 文件写入成功率 |
| 失败 | 失败 Step / 错误类型 / 是否扣费 |

**10 条 prompt 跑完后开一次复盘**,决定 v0.1 范围调整。

---

## 7. 验收标准（DoD）

- [ ] 10 条**真实可代表原型场景**的 prompt(登录页、列表页、卡片、图标、插画 各 2 条),都能跑出 PNG
- [ ] 每张图至少能看清主体(不出现"完全乱码"或纯色)
- [ ] 主观打分 ≥ 3/5 的比例 ≥ 60%
- [ ] 至少 1 位设计/产品同行交叉验证主观打分(避免自欺)
- [ ] 单次 4 张 < 60s(p95)
- [ ] 单次成本 < $1
- [ ] Trace JSON 字段与 `12-Trace数据模型.md` 设计对齐
- [ ] README 包含:跑法 / 已知问题 / 复盘结论 / 是否建议继续 v0.1

## 8. 退出条件（go / no-go 决策）

跑完尖刺后,写一份复盘,回答:

| 条件 | 结论 → 决策 |
| --- | --- |
| 业务质量达不到"3+ 占比 60%" | 🟡 换 model 名再跑一轮(仍 openai 协议);仍不行 → ❌ 回退首发场景到写标书 |
| 业务质量 OK,但成本 > $0.5/张 | 🟡 v0.1 默认 1 张,选项明示"批量更贵";或加 mock 模式 |
| 业务质量 OK,但中转站失败率 > 10% | 🟡 v0.1 必须先上 retry + 多 provider 备份 |
| 业务质量 OK + 成本可接受 + 链路稳 | ✅ 进 v0.1,路线图按 `09-MVP-路线图.md` 推进 |

## 9. 时间盒（self-imposed）

虽然用户说"不考虑时间",**尖刺必须有时间盒**,否则会变成"小 v0.1"。

- 上限:**1 天**(净开发,不含调研;生图链路天然短,比原写标书尖刺的 1 周更激进)
- 超出 → 强制减范围:去掉 normalize_prompt,直接传原始 prompt
