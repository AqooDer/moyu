# 04 - 总体架构

> 本文给出 Moyu 的总体架构、模块划分、进程模型与关键架构决策（ADR）。术语见 `03-核心概念定义.md`。
> 撰写日期：2026-05-20

---

## 1. 设计原则（按优先级）

1. **本地优先（Local-First）**：所有用户数据默认存本地；云调用走用户自己的 API Key。
2. **单一语言栈**：TypeScript 贯穿 UI → 服务 → Skill。避免 Python/Node 双语言带来的部署/打包复杂度。
3. **配置驱动 + 受控代码生成**：Agent 默认形态 = Manifest + 声明式 UI Schema + 装配现有 Skill；当 Meta-Agent 判定现有 Skill 不够时,可按受控模板生成新 Skill,但必走"静态检查 + 沙箱试跑 + 用户审核"三关（详见 ADR-003 / ADR-008 / `17`）。
4. **可观测优先**：每个 Step 都有 Trace；UI 内置 Run 详情视图。没有可观测就无法做监控智能体。
5. **协议开放**：工具走 MCP，模型走 Provider 抽象，不锁定单一厂商。
6. **可中断 / 可恢复**：长任务（如写标书）默认支持暂停 / 续跑 / 重放。

## 4. 进程模型

```
┌─ Electron Main Process ─────────────────────┐
│  窗口/菜单/更新；不做业务                     │
│                                              │
│  ┌─ Renderer (BrowserWindow) ──────────┐    │
│  │  React App；不做业务，全部走 IPC      │    │
│  └─────────────────────────────────────┘    │
│                                              │
│  ┌─ Core Subprocess (fork node) ───────┐    │
│  │  业务核心；HTTP/IPC 服务              │    │
│  │                                       │    │
│  │  ┌─ L1 Sandbox (worker_threads) ──┐  │    │
│  │  │  isolated-vm 跑 Skill 脚本     │  │    │
│  │  └────────────────────────────────┘  │    │
│  └───────────────────────────────────────┘    │
│                                              │
│  ┌─ L2 Sandbox (docker container) ─────┐    │
│  │  按需启动，用完即销毁                  │    │
│  └─────────────────────────────────────┘    │
└──────────────────────────────────────────────┘
```

**为什么 Core 走子进程而不是 Electron Main？**
- Main 进程阻塞会卡 UI；Core 里大量 LLM 调用是长 IO，必须隔离。
- 子进程崩溃可独立重启，不会带掉整个 App。
- 未来 Headless 模式（CLI / 服务端跑）直接复用 Core，不依赖 Electron。

## 5. 关键数据流

### 5.1 创建一个 Agent（Meta-Agent Flow）
```
用户在 UI 输入"我要一个写标书的 Agent"
   │
   ▼ (IPC)
Core/MetaAgent 收到 → 启动对话 Workflow
   │
   ├── 选 Recipe（如内置"标书"配方）作为 few-shot
   │
   ├── 多轮问答收集：评分维度、文档模板、字数要求…
   │
   ├── 生成 Manifest 草稿（YAML）
   │
   ├── Zod 校验 → 失败回到上一步让模型修
   │
   ├── 试运行（用一个最小输入跑一遍 Agent）
   │
   ├── 成功 → 入库（SQLite）+ UI 提示
   │
   └── 失败 → 把错误反馈给 Meta-Agent → 自我修复 → 重试
```

### 5.2 执行一个 Agent（Runtime Flow）
```
用户点"运行 → 上传招标文件.pdf" → Task 创建
   │
   ▼
Orchestrator 启动一个新 Run
   │
   ├── 读取 Agent Manifest → 装配 Skills/Tools
   │
   ├── Step 1: extract_bid_requirements (Skill)
   │     │
   │     ├── Router 选 Model (medium tier)
   │     ├── 在 L1 Sandbox 跑解析脚本
   │     └── 写入 Working Memory
   │
   ├── Step 2: generate_outline (Skill)  ← 串行 / 并行 由编排决定
   │
   ├── Step N: render_docx (Tool)
   │
   ├── 全部 Step 完成 → 产出 Artifact (.docx)
   │
   └── 写入 Trace；Monitor-Agent 异步消费
```

### 5.3 监控反馈环（Monitor Flow，异步）
```
每天定时（或累计 N 条 Trace 后）触发
   │
   ▼
Monitor-Agent 抽样最近 Trace
   │
   ├── 评估：成本 / 延迟 / 失败率 / 重试率
   │
   ├── 生成"路由规则建议"或"Manifest 修改建议"
   │
   ├── 入"待审核"队列
   │
   └── 用户在 UI 一键采纳/忽略
```

## 8. 架构决策记录（ADR）

> ADR 是只增不删的决策日志。后续每次重大变更新增一条，不修改历史。

### ADR-001 — 选 Electron，不选 Tauri
- **决策**：桌面壳用 Electron。
- **理由**：单人维护，TS 栈一致优先；Tauri 的 Rust 学习成本与生态成本高。
- **代价**：包体积约 150MB、内存占用偏高；用 `electron-builder` 优化打包。
- **触发重审条件**：包体积导致下载漏斗显著流失，或团队有 Rust 工程师加入。

### ADR-002 — Core 独立子进程
- **决策**：Core 不跑在 Electron Main 里，而是 `child_process.fork` 出来。
- **理由**：业务解耦、崩溃隔离、未来 Headless 复用。
- **代价**：多一层 IPC。
- **触发重审条件**：IPC 成为性能瓶颈（不太可能）。

### ADR-003 — 配置驱动 + 受控代码生成（2026-05-21 修订，详见 ADR-008）
- **原决策（2026-05-20）**：v0.x，Meta-Agent 只产出 Manifest + 装配 Skill；不生成新 Skill 代码。
- **修订决策（2026-05-21）**：Agent 的常态形态 = Manifest + **声明式 UI Schema** + 现有 Skill 装配；**Skill 代码可由 Meta-Agent 按需生成**,但必须满足：
  1. 单文件 < 150 行业务区,模板骨架锁定（详见 `17-Skill受控生成与审核.md §4`）
  2. 走完整 STATIC_CHECK → SANDBOX_DRY_RUN → HUMAN_REVIEW 流程,**默认不自动通过**
  3. 跑在 L1 沙箱（worker_threads + isolated-vm）,仅能调白名单 Host API
- **理由**：纯"装配现有 Skill"的天花板很低,Meta-Agent 一旦遇到内置 Skill 不覆盖的能力就只能向用户摆烂；引入受控生成后,既能扩表达力,又能借审核 + 沙箱兜住安全。
- **代价**：需建模板骨架 + ESLint 规则 + 沙箱试跑 + 审核 UI,工程量比"完全不生"大一档；审核回路给用户加一个心智负担。
- **触发重审条件**：审核拒绝率长期 > 50%（说明模板/few-shot 不够好）,或沙箱越权事件出现 → 立即收紧。

### ADR-003a — 声明式 UI 不走 React/JSX 生成
- **决策**：Agent 的 UI 由 YAML DSL 声明,平台运行时解释执行;Meta-Agent **不写 JSX/TSX/CSS**。
- **理由**：让 LLM 写任意前端代码 = 无法审、无法降级、无法热加载；YAML DSL 配合闭集控件,既给 Meta-Agent 自由度又把风险面收死。
- **代价**：控件目录是闭集,新增需平台升级 + ADR;复杂自定义 UI 走"自定义 Skill 渲 HTML 给 Iframe"逃生口（非主线）。
- **触发重审条件**：闭集控件 > 50% 的 Agent 觉得不够用 → 引入"组件组合"原语而不是放开 JSX。

### ADR-004 — Router 走规则，Monitor 走 LLM
- **决策**：模型路由是纯代码热路径；监控智能体异步优化路由规则。
- **理由**：避免每次调用都付 LLM 决策成本与延迟。
- **代价**：规则不如端到端学习灵活。
- **触发重审条件**：监控建议长期被采纳但仍劣化 → 引入轻量学习模型。

### ADR-005 — 沙箱 L1 用 isolated-vm，不用 vm2
- **决策**：JS 沙箱用 `isolated-vm`。
- **理由**：`vm2` 已废弃且有安全 CVE；`isolated-vm` 用 V8 Isolate，安全且性能好。
- **代价**：需要 native 编译，跨平台构建要 prebuild。
- **触发重审条件**：跨平台构建严重受阻 → 退回 worker_threads + 自实现 require 白名单。

### ADR-006 — 全本地存储 + BYO Key
- **决策**：用户数据全部本地；调云模型用户自带 Key。
- **理由**：隐私友好、合规友好、单人无运维负担。
- **代价**：用户首次配置门槛略高 → 用引导式 Onboarding 化解。
- **触发重审条件**：未来做托管版本 → 在 Core 上加一层 Cloud Adapter，本地架构不变。

### ADR-007 — Monorepo + pnpm workspaces
- **决策**：单仓库管理所有包。
- **理由**：跨包重构方便、类型贯通、CI 简单。
- **代价**：仓库变大。
- **触发重审条件**：单仓 > 10w 行 + 多团队协作 → 考虑拆库。

### ADR-008 — 把"agent create agent"做实（2026-05-21）
- **背景**：用户在 2026-05-21 review 中明确指出,如果 Meta-Agent 只能在预置 Recipe 里挑、不能产出"我没预想过"的能力,平台与"挑一个现成 Agent 用"无本质区别,**aca（agent create agent）这个核心定位就垮了**。同时把首发场景从"写标书"切到"生图原型 Agent"——这种场景天然要求 Meta-Agent 能造出形态各异的 UI（项目管理、图集、批量生成等）。
- **决策**：将 Meta-Agent 的产物从"Manifest + 装配现有 Skill"扩展为：
  1. **Manifest**（数据契约,见 `05 §3`）
  2. **声明式 UI Schema**（`ui.yaml`,见 `16`）—— Meta-Agent 生成,平台解释执行
  3. **可选自研 Skill 代码**(`skills/<name>/`,见 `17`) —— Meta-Agent 按需生成,必走审核 + L1 沙箱
  4. 物理形态 = **单 Agent 一个文件夹**(见 `15`),用户可外部编辑、git 管理、tar 导出
- **理由**：
  - 让 Meta-Agent 真的有"造未预想过的能力"的手段（受控但开放）
  - 声明式 UI + Skill 沙箱共同把"LLM 生代码"的风险面压到最小
  - 单文件夹形态把 Agent 从"数据库里的隐形对象"变成"用户拿得到、看得见、改得动的物件"——与 Claude Code 类工具的本质差异点
- **代价**：相比"只装配"路线,要多写三套基础设施（UI Schema 解释器 + Skill 模板 + 审核流程）;v0.2 Recipe 装配器先上,v0.3 开 Skill 生成,v0.5 才铺 workspace_views 等高级特性。
- **替代方案**：(a) 完全不生代码（原 ADR-003）—— 用户已否决；(b) 完全放开让 LLM 写 React/任意 TS —— 风险无法收敛,被 ADR-003a 与本 ADR 共同拒绝。
- **触发重审条件**：v0.3 demo 跑生图 Agent 时,Meta-Agent 自动生成的 Skill 长期被用户拒绝（> 50%）→ 退回"只装配 + 求助用户手写"路线,把"生"改成"提模板让用户填"。

## 9. 非功能性需求

| 维度 | 目标 |
| --- | --- |
| 启动时间 | 冷启动 < 3s（Electron + Core 都就绪） |
