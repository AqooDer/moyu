# 27 - 目标架构与大节点任务规划

> 本文描述 Moyu 的目标架构和后续大节点任务规划，不受当前原型完成度限制。后续开发按本文拆出的节点逐项闭环，当前实现状态仍以 `21` 为准。

## 1. 总体判断

Moyu 应该分成三层来推进：

1. **框架层 / Host + Harness**
   负责对话任务规划、任务管理、运行时、沙箱文件系统、插件/技能/MCP/内置工具接入、文件预览、异步执行、权限、Trace 和产物交付。
2. **Meta-Agent**
   负责通过对话生成 Agent，包括需求澄清、Agent 契约、Skill/Tool/MCP 装配、UI Schema、测试用例、验证运行和安装审核。
3. **Agent 对话与执行**
   负责用户和具体 Agent 的稳定对话体验：计划、执行、暂停、追问、调用工具、交付产物、恢复上下文、继续任务。

框架层是底座。Meta-Agent 和业务 Agent 都应该跑在同一套框架层能力上，而不是各自临时实现运行、文件、插件和对话状态。

## 2. 外部参考

### 2.1 Yuxi

参考：[Yuxi 首页](https://xerrors.github.io/Yuxi/)

Yuxi 与 Moyu 相似点很高，尤其是 Harness 方向。公开页面展示的关键模块包括：

- 沙盒文件系统：会话级 workspace / uploads / outputs，产物落盘，文本、图片、PDF、HTML 预览和下载
- Skills 技能系统：内置、上传、远程安装，解析草稿后确认安装
- MCP 集成：外部工具服务统一启停和权限管理
- 内置工具：产物交付、等待用户、按需安装技能、联网检索
- SubAgents：主智能体编排隔离子智能体，子线程执行复杂任务并回传产物
- 中间件编排：知识库检索注入、附件处理、历史摘要 offload、动态工具注入
- 异步 Worker：长任务后台执行，支持取消和流式输出

Moyu 不照搬 Yuxi 的企业级后端栈，但应该吸收它的 Harness 切分：文件系统、技能、工具、MCP、子智能体、中间件、异步任务必须是一等框架能力。

### 2.2 Claude Code

参考：

- [Claude Code overview](https://code.claude.com/docs/en/overview)
- [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)
- [Claude Code hooks](https://code.claude.com/docs/en/hooks)

可借鉴的稳定机制：

- 多 surface 共享同一引擎：终端、IDE、Desktop、Web 等入口围绕同一个执行核心
- 读项目、改文件、跑命令、接开发工具的 agentic loop
- 子智能体用于专门任务和上下文隔离
- hooks 让工具调用前后有可拦截、可审计、可自动化的生命周期点
- CLI 可组合，适合脚本、CI、批处理和自动化
- 长任务、远程继续、定时任务等机制把“对话”延伸成可管理工作流

Moyu 要学的是“对话机制和执行机制稳定”，不是代码工具定位本身。我们的任务对象更宽：文件、报告、图片、PPT、知识库和自定义 Agent。

### 2.3 Codex

Codex 官方手册在本次抓取中返回 403，因此本文不做官方细节断言。Moyu 可从 Codex 类客户端体验中吸收这些稳定模式：

- 任务先规划，再执行，再验证，再总结
- 工具调用和文件改动有清晰进度反馈
- 工作区隔离、权限边界、审批和可回滚很重要
- 长任务需要持续状态、可恢复上下文和最终验证记录
- 用户可以在过程中插话，系统要能接住新指令并调整当前任务

## 3. 框架层目标架构

框架层不是 UI 外壳，而是所有 Agent 的运行底座。目标模块如下：

```text
Framework Host
├── Conversation Orchestrator     # 对话任务规划、状态机、插话、追问、恢复
├── Work Manager                  # Work / Plan / Run 生命周期、队列、历史、归档
├── Execution Runtime             # plan -> step -> tool/skill/agent -> artifact
├── Sandbox Filesystem            # workspace / uploads / outputs / preview / download
├── Artifact Service              # 多格式产物登记、预览、版本、diff、交付
├── Plugin Registry               # Skills / Tools / MCP / previewers / middlewares
├── Permission & Policy Engine    # 权限、审批、敏感操作、配额、网络/文件边界
├── Middleware Pipeline           # RAG 注入、附件解析、历史摘要、动态工具注入
├── SubAgent Runtime              # 子智能体隔离、child run、结果回传
├── Async Worker                  # 长任务、取消、重试、流式事件、后台恢复
├── Trace & Observability         # 事件、日志、指标、回放、调试
└── Settings & Profiles           # 模型角色、知识库、插件、运行策略、Agent profile
```

### 3.1 你提到的框架层能力

你提到的三点应作为框架层核心职责：

- **整体对话任务规划、管理**：Work 不是一轮 chat，而是可计划、可中断、可恢复、可验证的任务会话。
- **外接插件**：插件不只包括 Skills / MCP，也包括文件预览器、解析器、导出器、中间件和权限策略。
- **文件预览**：必须从一开始设计为多格式，包括 Markdown、图片、PDF、DOC/DOCX、HTML、CSV/Excel、PPT、JSON、日志等。

### 3.2 框架层还应补充

- **计划与执行分离**：Plan 是可见、可确认、可调整的；Execution 是可追踪、可取消、可重试的。
- **事件总线**：所有运行状态通过事件流驱动 UI 和 Trace，避免 UI 猜状态。
- **会话级沙盒文件系统**：每个 Work/Run 有独立 workspace、uploads、outputs 和 temp。
- **产物生命周期**：Artifact 从创建、预览、编辑、版本、diff、采纳、回流知识库到导出，要有统一状态。
- **权限与审批**：文件写入、命令执行、网络访问、MCP 调用、安装插件、调用子智能体都要可声明权限和审批点。
- **中间件机制**：附件解析、RAG、历史摘要、动态工具注入、模型上下文压缩等都不要写死在 Agent 中。
- **长任务机制**：分钟级/小时级任务需要后台 worker、取消、重试、恢复和流式输出。
- **子智能体运行时**：子任务要有 child run、独立上下文和产物回传。
- **模型角色与路由**：先做角色和策略，再做复杂路由；所有模型选择写进 Trace。
- **观测与调试**：Trace 不只是记录结果，还要支持回放、问题定位、成本/耗时分析。
- **插件安全模型**：安装前解析、校验、权限声明、试跑、人工确认，运行时按能力边界执行。

## 4. 目标数据对象

当前 `Work / Run / Step / Artifact` 是正确方向，但目标形态需要扩展：

- `Workspace`：本地项目根、配置、插件、Agent、知识库
- `Project`：可选的业务项目分组
- `Work`：任务会话，用户感知主对象
- `Plan`：可见任务计划，包含阶段、依赖、确认点
- `Run`：一次执行
- `Step`：一次可观察执行动作
- `ToolCall` / `SkillCall` / `McpCall` / `AgentCall`
- `Artifact`：产物及版本
- `SandboxFile`：沙盒文件系统中的文件
- `Plugin`：Skill / Tool / MCP / Previewer / Middleware 的统一注册对象
- `Policy`：权限、配额、审批、敏感路径、网络域名
- `TraceEvent`：事件流和回放基础

## 5. 大节点路线

### P0 - 架构基线与任务系统

目标：先把路线本身固定成可执行计划，后续所有工作按节点闭环。

小任务：

- P0.1 固化本文为路线基线，并在 `docs/README.md` 入口可见
- P0.2 把 `25` 改造成阶段型任务清单，按 P0-P6 管理
- P0.3 定义每个节点的 DoD：文档、代码、测试、验证、演示路径
- P0.4 增加 Architecture Decision 记录位置，避免重大决策散落
- P0.5 建立每个阶段的最小 demo 标准

### P1 - 框架层完善

目标：建立稳定 Host/Harness，让任何 Agent 都能在同一套对话、文件、插件、运行和 Trace 机制中工作。

小任务：

- P1.1 Conversation Orchestrator：支持 plan、执行中插话、追问、用户确认、任务恢复
- P1.2 Work Manager：统一 Work / Plan / Run / Step 生命周期，支持状态恢复和历史检索
- P1.3 Execution Runtime：实现通用 step runner，支持 tool / skill / mcp / agent_call / user_checkpoint
- P1.4 Sandbox Filesystem：每个 Work/Run 拥有 workspace / uploads / outputs / temp
- P1.5 Artifact Service：统一产物登记、预览元数据、版本、diff、下载和交付
- P1.6 Previewer 插件：先支持 md、txt、json、图片、pdf、doc/docx，后续扩展 html、csv、xlsx、pptx
- P1.7 Plugin Registry：统一 Skills / Tools / MCP / Previewers / Middlewares 注册、启停和权限声明
- P1.8 Permission & Policy：文件、网络、命令、插件安装、MCP 调用、子智能体调用审批
- P1.9 Middleware Pipeline：附件解析、历史摘要、RAG 注入、动态工具注入
- P1.10 Async Worker：长任务后台执行、取消、重试、流式事件
- P1.11 Observability：事件流、TraceEvent、debug log、成本/耗时统计、回放入口

第一阶段验收 demo：

```text
用户上传 PDF/DOCX -> 框架解析成沙盒文件 -> Agent 制定计划 -> 执行多 step -> 生成 md/pdf/html 产物 -> 右侧预览 -> Trace 可回放 -> 可取消/恢复
```

### P2 - Meta-Agent 生成可运行 Agent

目标：Meta-Agent 不只是生成文件夹，而是真正生成“能在框架层跑起来”的 Agent。

小任务：

- P2.1 Agent Contract v1：manifest、ui、skills、tools、mcp、middlewares、policies、tests
- P2.2 需求澄清对话：Meta-Agent 自动追问目标、输入、输出、权限、工具、验收标准
- P2.3 Agent 规划器：根据需求选择 Agent 类型、执行模式、所需插件和 UI
- P2.4 Skill 生成与审核：支持 LLM Skill、配置型 Skill、代码型 Skill 的分级生成
- P2.5 Tool / MCP 装配：从 registry 中选择已有能力，不够时提出安装/生成请求
- P2.6 UI Schema 生成：生成输入表单、运行状态、产物视图、设置项
- P2.7 测试用例生成：为 Agent 自动生成 dry-run case 和最小验收用例
- P2.8 Sandbox dry-run：安装前在沙盒里跑通 demo
- P2.9 安装审核：文件 diff、权限 diff、测试结果、风险说明、版本化安装
- P2.10 Agent 迭代：根据运行失败、用户反馈、Trace 自动提出补丁

第二阶段验收 demo：

```text
用户说“做一个 PDF 转 PPT Agent”
  -> Meta-Agent 追问输入/模板/输出风格
  -> 生成 Agent contract + UI + skills + tests
  -> 沙盒 dry-run 产出示例 PPT
  -> 用户审核权限和 diff
  -> 安装后在 Agent 对话中真实运行
```

### P3 - Agent 对话机制

目标：让业务 Agent 的对话体验稳定、可控、可交付，而不是一次性 prompt 调用。

小任务：

- P3.1 Agent Chat Session：每个 Agent 有独立会话、记忆边界、上下文压缩策略
- P3.2 Plan-first 交互：复杂任务先给计划，用户可确认、修改、跳过
- P3.3 Ask-user checkpoint：信息不足时中断提问，而不是硬跑
- P3.4 Streaming execution：步骤、工具调用、产物生成、错误恢复都实时展示
- P3.5 Multi-artifact delivery：一次任务可交付多个产物，并标记 primary / intermediate / report
- P3.6 Artifact edit feedback：用户编辑或采纳产物后回写为反馈
- P3.7 Continue / resume：用户隔天回来能继续同一 Work
- P3.8 Failure recovery：失败时给出可操作下一步，支持从指定 step 重跑
- P3.9 SubAgent handoff：主 Agent 可把子任务交给子 Agent，回传结果和产物
- P3.10 Conversation quality eval：记录满意度、人工修改率、重跑率、失败原因

第三阶段验收 demo：

```text
用户和“投标文档 Agent”连续对话
  -> Agent 先规划
  -> 发现缺公司资料时追问
  -> 调用文档解析、知识库、生成器、校对器
  -> 交付多个版本产物
  -> 用户修改后反馈进入下一轮
  -> 第二天继续同一任务
```

### P4 - 知识与文件能力

目标：让 Moyu 处理真实文件和知识资产，不停留在 md/image 原型。

小任务：

- P4.1 文件解析接口：统一 parser contract
- P4.2 PDF parser：文本、表格、图片、页码、引用定位
- P4.3 DOC/DOCX parser：结构、标题、段落、表格、批注
- P4.4 Office exporter：docx / pptx / xlsx 生成与预览
- P4.5 HTML preview sandbox：安全预览 HTML 产物
- P4.6 Knowledge ingestion：解析结果进入知识库待审核队列
- P4.7 RAG middleware：Agent 按需检索并带引用回答
- P4.8 Knowledge write-back：产物采纳后进入知识库
- P4.9 文件权限策略：上传、生成、下载、删除、外部打开都进入 policy

### P5 - 插件生态

目标：让 Moyu 的能力能被用户和社区扩展。

小任务：

- P5.1 Plugin manifest：统一描述 Skill / Tool / MCP / Previewer / Middleware
- P5.2 插件安装流程：解析草稿、权限声明、静态检查、确认安装
- P5.3 插件运行权限：按 Agent / Workspace / Work 维度授权
- P5.4 本地插件开发模式：热加载、测试、打包
- P5.5 远程插件源：只做签名和版本，不默认信任远程代码
- P5.6 插件市场 UI：浏览、安装、升级、禁用、卸载
- P5.7 插件审计：运行记录、错误、成本、权限使用

### P6 - 产品化与多入口

目标：从本地原型走向可长期使用的客户端。

小任务：

- P6.1 桌面壳选型：Electron / Tauri / Web-only 的最终决策
- P6.2 多入口一致性：CLI、Workbench、Desktop 共享同一 Framework Host
- P6.3 配置中心：模型、Provider、知识库、插件、权限、沙盒策略可编辑
- P6.4 数据迁移：JSON store -> SQLite 或其他本地持久化
- P6.5 备份与导出：Agent、Work、Artifact、Trace、配置打包
- P6.6 本地安全：Keychain、敏感文件保护、审计日志
- P6.7 更新机制：版本升级、迁移脚本、插件兼容性检查

## 6. 推荐执行顺序

不要先追求“Meta-Agent 很聪明”。顺序应该是：

1. **P1 框架层先稳**
   没有稳定 Host/Harness，Meta-Agent 生成出来的 Agent 也没有地方可靠运行。
2. **P2 Meta-Agent 生成能跑的 Agent**
   先生成配置型/受控 Skill Agent，再逐步开放代码型 Skill。
3. **P3 Agent 对话体验**
   让用户真正愿意在一个 Work 里反复协作，而不是跑一条命令。
4. **P4 文件和知识能力**
   支撑真实业务文件，尤其是 PDF / DOC / PPT / 表格。
5. **P5 插件生态**
   在框架和安全模型成熟后开放扩展。
6. **P6 产品化**
   桌面壳、多入口、数据迁移和安全收尾。

## 8. Moyu 和 Yuxi 的差异

Yuxi 更像企业知识与智能体 Harness 平台，强调 RAG、知识图谱、团队权限和后端部署。

Moyu 应该更像本地优先的 Agent 创建与运行客户端：

- 对个人开发者和小团队更轻
- Agent = 可审查文件夹
- Meta-Agent 是核心差异化能力
- 多产物任务会话是一等对象
- 框架层先服务本地 Workbench，再考虑团队化和远程化
- 插件安全以本地可审查和人工确认优先

## 9. 决策原则

- 框架层能力必须先于“聪明 Agent”落地。
- 所有外部能力都走插件注册和权限声明。
- 所有长任务都必须可取消、可恢复、可追踪。
- 所有产物都必须进入 Artifact 生命周期。
- 所有 Agent 生成都必须有审核、测试和安装记录。
- 所有未来能力都要能映射到 Work / Plan / Run / Step / Artifact / Trace。
