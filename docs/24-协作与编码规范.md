# 24 - 协作与编码规范

> 适用于 Moyu 当前仓库的默认研发流程。目标不是增加流程负担，而是把每次需求和 bug 修复都收敛成可审查、可验证、可回滚的最小闭环。

## 1. 核心原则

1. **一个需求一个 Issue，一个 bug 一个 Issue**
2. **一个闭环一个 Commit**
3. **先写清单，再写代码**
4. **先定义完成标准（DoD），再实现**
5. **需求、代码、测试、验证、文档一起闭环**
6. **改动要外科手术式，禁止顺手扩 scope**

如果暂时没有外部 Issue 系统，至少要先创建一份本地任务清单，记录需求背景、验收标准、影响范围、测试与验证计划，再开始编码。

---

## 2. 提交流程

### 2.1 Issue / 任务拆分规则

- 一个需求只处理一个明确目标，不混入无关优化
- 一个 bug 只修一个根因链路，不顺带改另一个问题
- 功能开发和 bug 修复不要混在同一个提交里
- 重构只能服务于当前需求或当前 bug，不单独夹带“顺手整理”

### 2.2 标准工作流

1. 建 Issue 或本地任务清单
2. 写清验收标准、测试点、影响范围
3. 实现最小可行改动
4. 运行测试、手工验证、必要的回归验证
5. 同步文档、示例、配置说明
6. 按规范提交 Commit，并在清单中记录 Commit 做闭环

---

## 3. Commit Message 规范

格式：

```text
<type>(<scope>): <subject>
```

说明：

- 冒号 `:` 后必须有一个空格
- `scope` 选填，表示作用范围，可以是模块名、目录名、数据层、视图层等
- `subject` 必填，简短说明本次提交解决了什么
- 中英文都允许，但要简洁、可扫描

示例：

```text
feat(workbench): 增加设置中心与模型角色配置原型
fix(runtime): 修复 dry-run 下 artifact 数量统计错误
docs(process): 补充需求与 bug 闭环协作规范
refactor(meta): 收敛 agent 草案生成的文件写入逻辑
test(workbench): 增加设置数据导出与渲染断言
```

### 3.1 `type` 枚举

- `feat` - 新功能 feature
- `fix` - 修复 bug
- `docs` - 文档注释
- `style` - 代码格式（不影响代码运行）
- `refactor` - 重构、优化（不增加新功能，也不是修复 bug）
- `perf` - 性能优化
- `test` - 增加测试
- `chore` - 构建过程或辅助工具变动
- `revert` - 回退
- `build` - 打包相关

## 4. Karpathy 风格工程约束（并入本仓库规范）

结合 `karpathy-guidelines`，Moyu 默认遵守以下工程行为：

### 4.1 先想清楚再写

- 先写需求清单或 bug 清单
- 先说明验收标准、边界、假设
- 语义不清时先澄清，不允许靠“猜”推进核心逻辑

### 4.2 简单优先

- 只做当前需求明确要求的内容
- 不为单次使用场景提前抽象
- 不为“未来可能会用”而提前配置化
- 200 行能解决的问题，不要写成 500 行

### 4.3 外科手术式改动

- 每一行改动都必须能追溯到当前需求或当前 bug
- 不顺手修无关问题
- 不修改无关命名、注释、格式、目录结构
- 如果发现旁路问题，可以记录为后续 Issue，不在当前提交中偷带

### 4.4 以验证为目标

- 功能开发：要有明确验收与验证记录
- bug 修复：先复现，再修复，再防回归
- 行为变化：优先补测试
- 无法自动化测试时，必须留下手工验证步骤和结果

## 5. 需求开发规范

### 5.1 开始编码前必须具备

- 需求背景
- 目标用户 / 使用场景
- 明确范围（做什么 / 不做什么）
- 验收标准
- 影响模块
- 测试与验证方案

没有这些内容时，先补清单，不直接进入编码。

### 5.2 需求实现的默认 DoD

以下条目默认为完成定义的一部分：

- 代码实现完成
- 关键路径测试完成
- 手工验证完成
- 相关文档已同步
- 配置/脚本/示例已同步
- 清单中记录了 Commit，形成闭环

---

## 6. Bug 修复规范

### 6.1 开始修复前必须具备

- 现象描述
- 复现步骤
- 期望行为
- 实际行为
- 根因分析
- 修复策略
- 回归风险

### 6.2 Bug 修复的默认 DoD

- 能稳定复现原问题
- 修复后复现用例通过
- 有自动化测试则补回归测试
- 没法自动化时要有手工回归记录
- 相关文档/注释/说明已同步
- 清单中记录了 Commit，形成闭环

---

## 7. 文档同步规则

出现以下情况时，必须同步文档：

- 用户可见功能变化
- 命令、参数、配置项变化
- 信息架构、导航、设置项变化
- 数据结构、契约、运行方式变化
- 新增协作流程、约束、脚手架

最少同步以下之一：

- `README.md` / `README.zh-CN.md`
- `docs/*.md`
- 原型数据或示例文件

---

## 8. 测试与验证规则

### 8.1 默认要求

- 能写自动化测试就写自动化测试
- 改动会影响已有行为时，优先补回归测试
- 无法自动化时，记录手工验证步骤、输入、输出、结果

### 8.2 验证记录至少包含

- 验证命令
- 验证环境
- 验证输入
- 预期结果
- 实际结果

---

## 9. 推荐补充规范

以下规则建议作为团队默认习惯一并执行：

- **需求清单先行**：没有清单，不开始编码
- **禁止混合提交**：一个 Commit 不同时包含 feature + fix + 无关 refactor
- **先复现再修 bug**：避免“猜中就算修好”
- **配置变更显式化**：新增模型、知识库、Tool、MCP 配置时必须给默认值、用途说明、回退策略
- **UI 改动要给状态覆盖**：正常、空态、加载、失败至少覆盖到
- **Agent / Skill / MCP 相关改动要可追踪**：来源、默认行为、权限边界要能落到文档或配置
- **避免静默降级**：如果系统 fallback，要在 UI 或 Trace 中让用户看见
- **先定义角色再绑模型**：优先声明“用途角色”，如对话模型、切片模型、生图模型、规划模型，而不是把具体模型名写死在业务逻辑里
