# 24 - 协作与编码规范

> 本文是 Moyu 当前仓库的默认协作流程。目标是让每次需求、缺陷和文档调整都能形成可审查、可验证、可回滚的最小闭环。

## 1. 核心原则

1. 一个需求一个清单项。
2. 一个 bug 一个清单项。
3. 一个闭环一个 commit。
4. 先写清单，再改代码或文档。
5. 先定义验收标准，再实现。
6. 只改与当前任务有因果关系的内容。

没有外部 Issue 系统时，使用本地清单：

- [25 - 当前需求任务清单](./25-当前需求任务清单.md)
- [26 - 当前缺陷与质量修复清单](./26-当前缺陷与质量修复清单.md)

## 2. 工作流

需求：

1. 在 `25` 登记目标、范围、非范围、验收标准和验证方式。
2. 按最小可行范围实现。
3. 同步 README、docs、配置示例或 UI 文案。
4. 运行验证。
5. 回填验证结果和 commit。

缺陷：

1. 在 `26` 登记现象、复现、期望、实际、根因和回归风险。
2. 先复现或精确定义问题。
3. 用最小改动修复根因。
4. 补自动化测试或记录手工回归。
5. 回填验证结果和 commit。

## 3. Checklist

模板保留两份：

- [Feature Delivery Checklist](./checklists/feature-delivery-checklist.md)
- [Bugfix Delivery Checklist](./checklists/bugfix-delivery-checklist.md)

已完成的具体交付 checklist 不长期保留在主文档树中。历史追溯以 git history、commit message 和清单中的闭环记录为准。

## 4. Commit Message

格式：

```text
<type>(<scope>): <subject>
```

允许类型：

- `feat`
- `fix`
- `docs`
- `style`
- `refactor`
- `perf`
- `test`
- `chore`
- `revert`
- `build`

示例：

```text
feat(workbench): 增加设置中心独立状态与路由
fix(runtime): 修复 dry-run artifact 统计
docs(architecture): 重整 docs 文档体系
refactor(settings): 拆分设置领域源码目录
```

## 5. 文档同步

出现以下变化时必须同步文档：

- CLI 命令、参数或环境变量变化
- Agent 文件夹契约变化
- Run / Step / Artifact / Work / Message 数据结构变化
- Workbench UI / API / 路由变化
- Settings、模型角色、知识库、Skill、Tool、MCP 配置变化
- 新增或删除本地目录约定
- 用户可见行为变化

同步位置：

- 外部介绍：`README.md` / `README.zh-CN.md`
- 当前架构：`docs/03`、`04`、`05`、`06`
- Workbench：`docs/14`、`ui/workbench/README.md`
- 工程运行：`docs/21`
- 协作与清单：`docs/24`、`25`、`26`

## 6. 验证要求

默认验证：

```bash
npm test
npm run typecheck
npm run build
git diff --check
```

纯文档调整至少执行：

```bash
git diff --check
```

如果删除或重命名文档，还要用 `rg` 检查残留引用。

无法自动化验证的 UI 行为，需要记录：

- 浏览器地址
- 操作步骤
- 预期结果
- 实际结果
- 已知限制

## 7. 工程约束

- 不把设计方向写成当前实现。
- 不把本地 `.env`、API key、私密 base URL 写入仓库。
- 不把 `artifacts/`、`traces/`、`dist/`、`node_modules/` 纳入版本库。
- 不在业务逻辑中硬编码具体模型名，优先使用 model role。
- 不静默覆盖 Agent；冲突必须给出下一步。
- 不执行未审核的生成代码。
- 不把无关重构夹进当前任务。

## 8. 完成定义

一个任务完成时应满足：

- 清单状态已更新。
- 实现或文档改动已完成。
- 相关文档已同步。
- 验证已运行或说明未运行原因。
- commit message 符合规范。
- 清单记录 commit 或等待 commit 的占位说明。
