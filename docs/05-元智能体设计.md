# 05 - Agent 与 Meta-Agent 设计

> 本文合并原先分散在 Agent 文件夹结构、声明式 UI Schema、Skill 受控生成和 Meta-Agent 设计中的当前有效内容。当前实现以 `src/agent/` 和 `src/meta/` 为准。

## 1. Agent 文件夹契约

Agent 是本地可审查文件夹。当前仓库通过 `src/agent/registry.ts` 读取 Agent，通过 `src/agent/validate.ts` 校验 Agent。

最小目录：

```text
agents/<agent_folder>/
├── manifest.yaml
├── ui.yaml
├── README.md
├── history/
└── skills/
```

推荐目录：

```text
agents/<agent_folder>/
├── manifest.yaml
├── ui.yaml
├── README.md
├── .agentignore
├── agent.recipe.ts
├── prompts/
│   └── system.md
├── skills/
│   └── <skill_name>/
│       ├── skill.yaml
│       └── index.ts
├── history/
│   ├── <timestamp>-initial-create.meta.json
│   └── <timestamp>-initial-create.patch
└── verification.trace.json
```

逻辑 ID 与目录名：

```text
image-gen/prototype-v1 -> image-gen__prototype-v1
custom/image-prototype-v3 -> custom__image-prototype-v3
```

## 2. `manifest.yaml`

当前 registry 读取的字段：

- `agent_id`
- `name`
- `description`
- `version`
- `recipe_ref`
- `ui_ref`
- `tags`
- `mcp_servers`

当前 validator 要求文件文本包含：

- `schema_version:`
- `agent_id:`
- `workflow:`
- `inputs_schema:`
- `outputs_schema:`

Meta-Agent 生成的 manifest 还会写入：

- `routing.model_roles`
- `mcp_servers`
- `permissions`
- `created_at`

模型角色覆盖示例：

```yaml
schema_version: "1"
agent_id: image-gen/prototype-v1
name: Image Prototype
version: 0.1.0
recipe_ref: image-gen/prototype-v1
ui_ref: ./ui.yaml
routing:
  model_roles:
    image-generation:
      provider: openai-compat
      model: gpt-image-2
mcp_servers:
  - id: analytics-db-mcp
    transport: stdio
    state: review
    permissions: [database.query.read]
workflow:
  kind: sequence
inputs_schema:
  type: object
  required: [prompt]
outputs_schema:
  type: object
```

`mcp_servers` 是 Agent 能力装配声明，可以先写字符串 ID，也可以写对象形式保留 transport、state、description 和 permissions。当前运行器会把 MCP 装配快照写入 Run Trace 和 Workbench 数据，但尚未启动真实 MCP Server，也未执行 MCP 调用。

当前运行器只读取 summary、模型角色和 MCP 装配相关字段，尚未执行通用 `workflow`。

## 3. `ui.yaml`

`ui.yaml` 是 Agent 的声明式 UI 契约。当前 validator 要求包含：

- `schema_version:`
- `intake:`
- `output:`

当前 Workbench 尚未解释任意 Agent 的 `ui.yaml` 动态生成完整界面；它主要作为 Meta-Agent 生成草案的一部分供用户审核。设计原则仍保留：

- Meta-Agent 生成声明式 UI，不生成 JSX / React 代码
- 控件闭集，平台解释渲染
- 失败时可以降级为表单和文件列表

最小结构：

```yaml
schema_version: "1"
intake:
  fields:
    - id: prompt
      type: textarea
      label: Prompt
      required: true
output:
  views:
    - id: images
      type: artifact_gallery
      accepts: [png, jpg, webp]
run:
  primary_action:
    id: run
    label: Run
```

## 4. Skill

Skill 当前是 Agent 文件夹内的能力声明和代码组织方式，不是动态插件系统。

生图 Agent 的 Skill 目录：

```text
skills/image_gen_via_relay/
├── skill.yaml
└── index.ts
```

当前 `src/agent/run.ts` 直接执行生图原型逻辑，并没有动态 import 任意 Skill。后续受控生成 Skill 需要补齐：

- 静态检查
- 权限白名单
- sandbox dry-run
- 人工审核
- 安装前 diff
- 运行时可观察事件

在这些能力落地前，不应把 Meta-Agent 描述成“可安全生成并执行任意代码”。

## 5. Meta-Agent 创建草案

入口：

```bash
npm run dev -- meta create-agent --prompt "<需求>"
```

Workbench API：

```text
POST /api/meta/create-agent
POST /api/meta/conversation
```

当前流程：

1. 读取用户 prompt。
2. 推导 Agent ID、名称、描述、Recipe ref 和 Skill 名称。
3. 创建 Meta Run 和 Work。
4. 写入 Agent 草案文件夹。
5. 校验 Agent 文件夹契约。
6. 写 `verification.trace.json`。
7. 写 `agent-draft.json` 和全局草案索引。
8. 把草案文件注册为 Artifact。
9. 写 `traces/<run_id>/run.json`。
10. 写 Work / Message，Workbench 可恢复会话。

默认输出位置：

```text
artifacts/meta-agent-runs/<run_id>/<agent_folder>/
```

如果使用 `--persist`，会直接写入 `agents/`，但日常推荐先生成草案再安装。

Workbench 对话式创建走更严格的 LLM 链路：

- 每轮 `/api/meta/conversation` 都要求已配置 `MOYU_LLM_PROVIDER_BASE_URL` 和 `MOYU_LLM_PROVIDER_API_KEY`。
- 对话模型返回结构化决策：继续追问、等待确认或开始创建。
- 用户确认创建后，`createAgentWithMeta` 会强制使用 LLM 生成 Agent spec；缺配置、provider 失败或 JSON 非法都会报错，不回退为本地规则草案。
- CLI `meta create-agent` 仍保留本地规则 fallback，用于离线脚手架和兼容旧流程。

## 6. AgentDraft

AgentDraft 是 Meta-Agent 草案的状态记录。当前会出现在：

- 草案同级的 `agent-draft.json`
- `artifacts/meta-agent-runs/agent-drafts.json` 查询索引

关键字段：

- `runId`
- `agentId`
- `draftPath`
- `targetPath`
- `state`
- `validation`
- `createdAt`
- `updatedAt`
- `installedAt`

常见状态：

- `drafted`
- `validation_failed`
- `installed`
- `install_conflict`

## 7. 安装草案

入口：

```bash
npm run dev -- meta install-agent --run <run_id>
```

Workbench API：

```text
POST /api/meta/install-agent
```

安装流程：

1. 通过 Run Artifact 找到草案 `manifest.yaml`。
2. 定位草案 Agent 文件夹。
3. 校验草案。
4. 计算目标路径 `agents/<agent_folder>`。
5. 目标不存在时复制草案。
6. 校验安装结果。
7. 更新 AgentDraft 和 Work 状态。

默认不允许静默覆盖已存在 Agent。

## 8. 安装冲突

当目标 Agent 已存在时，安装接口返回冲突，并提供下一步：

- 创建新版本：`POST /api/meta/install-agent/version`
- 查看差异：`GET /api/meta/install-agent/diff?runId=<run_id>`
- 放弃安装：前端清除当前冲突态，不改本地 Agent

创建新版本会把 `custom/foo-v1` 安装为下一个可用版本，例如 `custom/foo-v2`。

差异接口当前提供文件级摘要：

- source only
- target only
- changed
- unchanged

逐文件可视化合并器尚未实现。

## 9. 校验边界

当前校验是结构性校验，不是安全审核：

- 能发现必备文件 / 目录缺失
- 能发现 manifest / ui 基本字段缺失
- 不执行 TypeScript 编译
- 不执行 Skill 静态安全扫描
- 不执行 sandbox dry-run
- 不理解完整 workflow 语义

因此生成 Agent 仍必须人工审核。

## 10. 与运行时的关系

Meta-Agent 本身也写 Run Trace。创建草案时产生的文件会作为 Artifact 注册，所以 Workbench 可以直接在右侧查看草案文件、验证记录和安装状态。

安装成功后，`agent list` 和 Workbench Agents 列表会从 `agents/` 重新读取正式 Agent。

## 11. 后续设计方向

- 用 LLM 做多轮需求澄清和规格生成
- 把 `agent.recipe.ts` 演进为真实 Recipe / workflow engine
- 动态解释 `ui.yaml`
- 受控生成 Skill 代码并运行安全检查
- Agent folder 热加载和外部编辑冲突检测
- Agent 导入 / 导出包
- AgentDraft 数据层版本化和查询 API
- 安装冲突逐文件合并器
