# 05 - 元智能体设计

> 元智能体（Meta-Agent）是 Moyu 的"造物主"：用户通过对话告诉它想要什么，它产出一个可直接运行的 Agent Manifest。
> 本文定义 Meta-Agent 的工作流程、对话策略、Manifest schema、装配机制、校验与自我修复回路。
>
> 术语对齐 `03-核心概念定义.md`，架构对齐 `04-总体架构.md`。
> 撰写日期：2026-05-20

---

## 1. 目标与非目标

### 1.1 目标
1. 用户用自然语言描述需求 → 平台产出一个**可直接运行**的业务 Agent。
2. 生成的 Agent **稳定可调试**（不是一次性魔法）。
3. 用户可以反复修改 Agent（"再给标书 Agent 加一个图表生成能力"）。
4. 失败可见、可修复（错误信息直接展示给用户而不是黑盒重试）。

### 1.2 非目标（v0.x）
- ❌ 不做"Agent 自我演化"（Agent 不会自己改自己的 Manifest）。
- ❌ 不预测用户没说的需求（宁可问也不猜）。
- ⚠ **Meta-Agent 写 Skill 代码**:原 ADR-003 禁止;2026-05-21 ADR-008 改为**受控开放**(模板 + 静态检查 + 沙箱试跑 + 必审),详见 `17-Skill受控生成与审核.md`。本文 §6.5 / §7 / §10 提到的"生成 Skill"均按 ADR-008 + 17 号文档执行。

### 1.3 范围分阶段（与 09 路线图对齐）
- **v0.2(Recipe 装配器)**：Meta-Agent 只为已选 Recipe 填空槽位 + 让用户裁剪可选 Step,**不生 UI、不生 Skill**。成功口径 = 稳定造出 3 类内置 Recipe Agent(写标书 / PDF→PPT / 长文翻译)。
- **v0.3(声明式 UI + LLM Skill 生成)**:Meta-Agent 开始产出 `ui.yaml`(见 `16`);可生成 `kind: llm` 的 Skill(走简化审核流,见 `17 §11`)。
- **v0.4(code Skill 生成)**:Meta-Agent 可按 `17 §3` 完整状态机生成 TS 代码 Skill;L1 沙箱必须已就绪。
- **v0.5+(workspace_views + 高级特性)**:UI Schema 支持 Workspace 级视图;Skill 模板库扩充。
- 本文档下文描述的状态机已涵盖 v0.4 形态;v0.2/v0.3 通过"跳过相应子状态"实现,不另写一份。

## 2. 元智能体工作流（State Machine）

```
                    ┌──────────────┐
       开始 ───────►│ INTAKE       │  需求收集（多轮对话）
                    │ (意图澄清)   │
                    └──────┬───────┘
                           │ 用户确认意图
                           ▼
                    ┌──────────────┐
                    │ RECIPE_PICK  │  选择最匹配的内置 Recipe（无则空白）
                    └──────┬───────┘
                           │
                           ▼
                    ┌──────────────────────────┐
                    │ SPEC_DRAFT                │  生成 Manifest 草稿
                    │  ├─ UI_DRAFT(v0.3+)       │  → 生成 ui.yaml
                    │  └─ SKILL_REQUEST(v0.3+)  │  → 缺 Skill 时进 17 号子状态机
                    │     ↓ SKILL_REVIEW        │     用户审核新 Skill
                    └──────────┬───────────────┘
                               │
                               ▼
                    ┌──────────────┐
                    │ VALIDATE     │  Zod schema + 引用完整性 + UI/Skill 校验
                    └──────┬───────┘
                  失败 ┌───┴───┐ 成功
                       ▼       ▼
              ┌─────────────┐ ┌──────────────┐
              │ SELF_FIX    │ │ DRY_RUN      │  最小输入试跑(含 UI 渲染冒烟)
              │ (限重试 3)  │ └──────┬───────┘
              └──────┬──────┘  失败 ┌┴┐ 成功
                     │              ▼ ▼
                     └──────────┐  ┌─────────────┐
                                │  │ HUMAN_REVIEW│  展示 Manifest + ui.yaml +
                                ▼  │ + 用户确认  │  新 Skill diff + Trace
                          ┌─────────┴─────┐  │
                          │ PERSIST       │ ─┘
                          │ 入 Agent 文件夹│  (见 15 号文档目录契约)
                          └───────────────┘
```

### 状态说明
| 状态 | 进入条件 | 出口 | 说明 |
| --- | --- | --- | --- |
| `INTAKE` | 用户开始新建 Agent | 用户明确意图 | 多轮提问,不允许跳过 |
| `RECIPE_PICK` | INTAKE 完成 | 选定 Recipe 或确认无 Recipe | 由 Meta-Agent 自动判断 |
| `SPEC_DRAFT` | Recipe 选好 | 产出 Manifest YAML | 一次 LLM 调用 |
| `UI_DRAFT`(v0.3+) | SPEC_DRAFT 完成 | 产出 `ui.yaml`(见 16) | 走 16 号文档闭集控件;v0.2 跳过(走平台兜底 UI) |
| `SKILL_REQUEST`(v0.3+) | SPEC_DRAFT 判定现有 Skill 不够用 | 进入 17 §3 子状态机 | 用户必须先同意"可以生" |
| `SKILL_REVIEW`(v0.3+) | SKILL_REQUEST 跑完 STATIC_CHECK + SANDBOX_DRY_RUN | 用户采纳 / 修改 / 拒绝 | 详见 17 §7 |
| `VALIDATE` | Draft 完成 | 校验通过 / 失败 | 纯代码;含 `ui.yaml` schema 校验 |
| `SELF_FIX` | VALIDATE 失败 | 修复后回 VALIDATE | 最多 3 次,超出转人工 |
| `DRY_RUN` | VALIDATE 通过 | 试跑成功 / 失败 | 用 Recipe 自带的 minimal input;v0.3+ 还会冒烟渲染一次 UI |
| `HUMAN_REVIEW` | DRY_RUN 成功 | 用户确认 / 退回修改 | UI 展示 Manifest + ui.yaml diff + 新 Skill 审核结果 + Trace |
| `PERSIST` | 用户确认 | Agent 落到 `agents/<agent-id>/`(见 15 号文档) | 终态;同时写 `history/initial-create.patch` |

### 2.1 v0.2 / v0.3 / v0.4 跑通哪些状态

| 状态 | v0.2 | v0.3 | v0.4 |
| --- | --- | --- | --- |
| INTAKE / RECIPE_PICK / SPEC_DRAFT | ✅ | ✅ | ✅ |
| UI_DRAFT | ❌(走平台兜底) | ✅ | ✅ |
| SKILL_REQUEST / SKILL_REVIEW | ❌ | ✅(仅 `kind: llm`) | ✅(含 code Skill) |
| VALIDATE / SELF_FIX / DRY_RUN / HUMAN_REVIEW / PERSIST | ✅ | ✅ | ✅ |

## 3. Agent Manifest Schema（YAML）

Manifest 是 Meta-Agent 唯一的产出形态。下面是**完整字段**与示例。

### 3.1 顶层结构（Zod 伪代码）

```ts
const AgentManifest = z.object({
  // ─── 标识 ─────────────────────────────────────────
  schema_version: z.literal("1"),
  id: z.string().uuid(),
  name: z.string().min(1).max(40),
  description: z.string().min(1).max(280),
  version: z.string().regex(/^\d+\.\d+\.\d+$/),     // SemVer
  icon: z.string().optional(),                       // emoji 或路径
  tags: z.array(z.string()).default([]),

  // ─── 行为 ─────────────────────────────────────────
  system_prompt: z.string().min(1),
  recipe_id: z.string().optional(),                  // 来自哪个 Recipe

  // ─── 能力装配 ────────────────────────────────────
  skills: z.array(SkillRef),                         // 装配的 Skill
  tools: z.array(ToolRef),                           // 装配的 Tool（含 MCP）

  // ─── 模型与路由 ──────────────────────────────────
  model_tiers: z.array(z.enum(['tiny','small','medium','large','frontier'])),
  routing_overrides: z.record(z.string()).optional(),  // step_name -> tier

  // ─── 记忆 ─────────────────────────────────────────
  memory: z.object({
    working: z.boolean().default(true),
    episodic: z.boolean().default(false),
    semantic: z.object({
      enabled: z.boolean(),
      collections: z.array(z.string()).optional(),
    }).default({ enabled: false }),
    shared_read: z.array(z.string()).default([]),
    shared_write: z.array(z.string()).default([]),
  }),

  // ─── 沙箱 ─────────────────────────────────────────
  sandbox: z.object({
    level: z.enum(['L0','L1','L2']).default('L1'),
    quota: z.object({
      max_cpu_seconds: z.number().default(120),
      max_memory_mb: z.number().default(512),
      max_wall_seconds: z.number().default(600),
      max_tokens: z.number().default(200_000),
    }),
    capabilities: z.object({
      fs_read: z.array(z.string()).default([]),       // glob 白名单
      fs_write: z.array(z.string()).default([]),
      net_domains: z.array(z.string()).default([]),
    }),
  }),

  // ─── IO 契约 ─────────────────────────────────────
  inputs_schema: JsonSchema,                          // JSON Schema
  outputs_schema: JsonSchema,

  // ─── 工作流 ─────────────────────────────────────
  workflow: z.discriminatedUnion('kind', [
    z.object({ kind: z.literal('react'), max_loops: z.number().default(20) }),
    z.object({ kind: z.literal('sequence'), steps: z.array(StepRef) }),
    z.object({ kind: z.literal('dag'), nodes: z.array(DagNode), edges: z.array(DagEdge) }),
  ]),

  // ─── 元信息 ─────────────────────────────────────
  created_by: z.enum(['meta-agent', 'user', 'import']),
  created_at: z.string().datetime(),
  updated_at: z.string().datetime(),
});
```

  kind: dag
  nodes:
    - id: extract
      skill: builtin/pdf/extract-sections@1.x

    - [extract, scoring]
    - [extract, outline]
    - [scoring, outline]

    - [write, render]

updated_at: 2026-05-20T10:15:00Z

## 4. 对话策略

### 4.1 三层 Prompt
Meta-Agent 自身用一个**固定的、强模型绑定**（如 Opus 4.7）的 system prompt，分三段：

1. **角色与契约**：你是 Meta-Agent，唯一目标是产出有效 Manifest，不要回答其他无关问题。
2. **可用资源清单**（运行时动态注入）：当前 Workspace 内可用的 Skill / Tool / Recipe / Model Tier 列表（含描述）。
3. **输出协议**：必须以严格 JSON 块返回结构化决策（state transition + payload）。

### 4.2 槽位收集（Slot Filling）
INTAKE 阶段不让模型自由聊天，强制按槽位推进。每个 Recipe 定义自己的 **必填槽位**：

```yaml
# Recipe: highway-v1
intake_slots:
  - key: scoring_dimensions
    question: "招标文件的评分维度有哪些？（可粘贴目录，也可以稍后补）"
    required: true
    type: text
  - key: target_word_count
    question: "技术标总字数大概多少？"
    required: false
    type: number
  - key: company_profile
    question: "用哪个公司档案？"
    required: true
    type: enum_from_storage
    source: shared.company-profile
```

UI 渲染时把槽位变成卡片式表单 + 自由对话双通道。

### 4.3 Recipe 机制
**Recipe** 是平台内置的"Agent 模板"，包含：
- 推荐的 Skill / Tool 组合
- 推荐的 system_prompt 框架（用户可改）
- 必填槽位
- minimal input（用于 DRY_RUN）
- 验收用例（可选）

**为什么需要 Recipe？**
- 从零让 LLM 想"标书 Agent 该装什么"很不稳定。
- 用 Recipe 做 few-shot，把成功率从~50% 拉到 ~90%。
- 用户也能在 UI 看到"标书 / PPT / 翻译 / 数据分析" 这些品类入口。

v0.x 内置 Recipe 清单（建议）：
- `bidding/highway-v1` — 高速公路技术标
- `bidding/waterway-v1` — 航道工程技术标
- `doc/pdf-to-ppt` — PDF → 教学 PPT
- `doc/long-translate` — 长文翻译
- `data/csv-insight` — CSV 数据分析报告

## 5. 校验（VALIDATE）

校验是**纯代码**，不用 LLM。包括：

| 检查项 | 方法 | 失败处理 |
| --- | --- | --- |
| Schema 合规 | Zod parse | 错误反馈给 SELF_FIX |
| Skill / Tool / Recipe 引用存在 | Registry 查表 | 同上 |
| 版本约束（`@1.x`）能解析 | semver | 同上 |
| Sandbox capability 路径合法 | path 白名单匹配 | 同上 |
| inputs_schema / outputs_schema 是合法 JSON Schema | Ajv | 同上 |
| 模型 Tier 至少有一个对应可用 Provider | Router 反查 | 警告（不阻断） |
| Workflow DAG 无环 | 拓扑排序 | 错误反馈 |

校验报告以**机器可读 + 人类可读双格式**返回，机器可读那份直接喂回 LLM 自修。

## 6. 自我修复（SELF_FIX）

```
VALIDATE 失败
    │
    ▼
把【原 Manifest + 错误列表 + Schema 文档摘要】喂回 Meta-Agent
    │
    ▼
要求模型只输出"差异 patch（JSON Patch）"，不重新输出整份 Manifest
    │
    ▼
应用 patch → 回 VALIDATE
    │
    ├── 通过 → 继续
    │
    └── 仍失败 → 计数器 +1
              超过 3 → 转 HUMAN_REVIEW（带完整失败上下文）
```

**为什么用 JSON Patch 而不是整文件重写？**
- 减少 token、减少 Diff 噪声。
- 模型聚焦修错的点，少引入新错。
- UI 可以高亮修改痕迹。

## 7. 试运行（DRY_RUN）

```
取 Recipe 的 minimal_input（例如：5 页的迷你招标 PDF）
    │
    ▼
按 Manifest 实际跑一次完整 Run（走真实 Sandbox）
    │
    ├── 全部 Step 成功 + 产出符合 outputs_schema → ✅
    │
    └── 失败 → 把 Trace 关键片段（错误 Step + 上下游 IO）喂回 Meta-Agent
            决定：
            ├── 是 Manifest 配置问题 → 回 SPEC_DRAFT 修改
            └── 是平台/Skill bug → 转 HUMAN_REVIEW，不要让模型瞎改
```

**关键约束**：
- DRY_RUN 必须用真实 Sandbox（不能 mock），否则上线后才发现 ENV 不对。
- DRY_RUN 资源消耗记入用户账（让用户感知成本）。
- 用户可以"跳过 DRY_RUN"，但默认开启。

## 8. 人工兜底（HUMAN_REVIEW）

UI 展示：
- Manifest YAML（折叠/展开）
- DRY_RUN Trace（每个 Step 的 input/output/耗时/Token）
- 校验/修复历史
- 三个按钮：
  - ✅ 采纳并保存（PERSIST）
  - ✏️ 我手动改一下（直接进 YAML 编辑器）
  - 🔁 让 Meta-Agent 再试（带我的修改意见）

## 9. Agent 修改与版本

- Agent 的 `version` 走 SemVer。
- 通过对话修改时，Meta-Agent 默认 bump patch（0.1.0 → 0.1.1）；
  - 装/卸 Skill 或 Tool → bump minor；
  - inputs/outputs schema 不兼容变化 → bump major。
- 每次修改保留旧版（SQLite 软删除），UI 提供"回退"。

## 11. 失败案例与处理

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 用户描述太模糊 | INTAKE 槽位没填全 | 不进 SPEC_DRAFT，继续提问 |
| Recipe 找不到匹配 | 是新品类 | 走"空白模板"，让用户多答几轮 |
| Manifest YAML 反复校验失败 | 模型不稳定 | 3 次后转人工，并把这次失败采样到训练集 |
| DRY_RUN 一直失败 | 内置 Skill 有 bug | 不让模型修，直接抛出，记 issue |
| 用户改了 Manifest 但跑不通 | 引用过时 | UI 高亮失效引用并建议替代 |
