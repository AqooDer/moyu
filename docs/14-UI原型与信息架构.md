# 14 - Workbench 与信息架构

> 本文是当前 Workbench 的产品与前端结构说明。旧 UI 线框、产品定位调整和任务会话式 Workbench 方案已经合并到这里。

## 1. 定位

Workbench 是 Moyu 的本地工作台，不是营销页，也不是节点画布编辑器。当前第一屏就是可用工作界面：

- 左侧：Work、Agent、设置入口
- 中间：任务会话、Meta-Agent 创建区、Agent run 输入区
- 右侧：Artifact、Trace、Details、Settings inspector

核心心智是“任务会话 + 多产物 + 可追踪运行过程”。画布视图可以作为后续观察工具，但不是当前 MVP 主路径。

## 2. 目录结构

```text
ui/
├── workbench/
│   ├── README.md
│   ├── index.html
│   ├── public/data/workbench.json
│   └── src/
│       ├── app.js
│       ├── styles.css
│       └── modules/
│           ├── install-module.js
│           └── settings-module.js
└── workbench-prototype/
    └── index.html
```

`ui/workbench/` 是当前正式前端结构。`ui/workbench-prototype/` 只保留旧路径兼容入口。

当前前端是原生 HTML / CSS / JavaScript，没有 React / Vite / Tailwind 构建链。

## 3. 打开方式

推荐使用本地服务：

```bash
npm run workbench:serve
```

默认地址：

```text
http://127.0.0.1:4177/ui/workbench/
```

如果端口被占用，服务会自动使用下一个可用端口，并在终端打印真实 URL。

静态预览：

```bash
npm run workbench:export-data
```

然后用普通静态服务或直接打开页面查看。静态预览模式无法执行创建、安装、运行、打开本地文件等 API 动作，页面应提示用户切回本地服务。

## 4. 信息架构

### 4.1 左侧栏

左侧栏负责选择上下文：

- Work 列表：来自 `artifacts/workbench/work-store.json` 和 Run history
- Agent 列表：来自 `agents/`
- Settings 入口：通过 hash 路由进入 `#settings/<section>`

左侧 Work 标题优先使用运行 prompt，避免同类 Agent 多次运行时难以区分。

### 4.2 中间区域

中间区域是任务会话：

- 展示用户消息、Agent summary 和产物引用
- 提供 Meta-Agent 创建 Agent 草案入口
- 提供当前 Agent dry-run / run 入口
- 显示操作状态、禁用原因和错误反馈

当前默认中文，支持 English 切换。

### 4.3 右侧 Inspector

右侧是当前上下文检查器：

- Trace：Run / Step / model roles
- Artifacts：产物列表和文本预览
- Context：Execution Mode、Sandbox Filesystem、Middleware Pipeline、Policy Evaluation、Worker Job 和 TraceEvent timeline
- Details：Agent、Run、路径和状态
- Settings：模型、知识库、Skill、Tool、MCP、Runtime 结构

dry-run 无产物时应展示空态，并引导查看 Trace。

## 5. Settings Center

Settings 是 Agent 架构面板，不是杂项页。当前分组：

- `overview`
- `models`
- `agent-context`
- `knowledge`
- `skills`
- `tools`
- `mcp`
- `runtime`

直达路由示例：

```text
#settings/models
#settings/knowledge
#settings/mcp
#settings/runtime
```

数据入口：

```text
GET /api/settings
```

当 `/api/settings` 不可用时，前端会尝试回退到 `/api/workbench` 或静态 `workbench.json` 内的 settings 数据。

当前 Settings 只读，不提供编辑保存。

## 6. Workbench API

本地服务由 `src/ui/server.ts` 提供。主要 API：

```text
GET  /api/health
GET  /api/workbench
GET  /api/settings
GET  /api/plugins
GET  /api/policies
GET  /api/works
GET  /api/messages
GET  /api/agents
GET  /api/meta/agent-drafts
GET  /api/runs/:id
GET  /api/artifacts/:id
GET  /api/artifact-preview?id=<artifact_id>
GET  /api/artifact-content?id=<artifact_id>
POST /api/artifact/open
POST /api/run/open-trace
POST /api/meta/create-agent
POST /api/meta/install-agent
POST /api/meta/install-agent/version
GET  /api/meta/install-agent/diff?runId=<run_id>
POST /api/agent/run
```

这些 API 都是本地服务 API，不是远程 SaaS API。

`GET /api/works` 返回 Work Manager v1 的只读 `WorkSummary`，包含 `storedState`、`runIds`、`currentRunId`、`lifecycle` 和 `progress`。它会从 WorkStore 与 Run Trace 恢复任务生命周期，不提供状态写入、取消、重试或恢复执行。

`GET /api/workbench` 的 `selectedRun` 会暴露运行时装配快照：`plan`、`execution`、`sandbox`、`middleware`、`policy`、`worker`、`events`、`modelRoles`、`mcpServers` 和 `steps`。右侧 Context tab 使用 `selectedRun.execution` 展示执行模式、入口、queue、dry-run effective、capability states 和 constraints，使用 `selectedRun.sandbox` 展示 Run 级文件系统 root、目录、writable、cleanup policy 和 constraints，使用 `selectedRun.middleware` 展示附件入口、历史摘要、知识上下文和能力注入阶段，使用 `selectedRun.policy` 展示策略总览、检查项、权限、关联能力和风险状态，使用 `selectedRun.worker` 展示 inline worker 的 state、queue、attempt 和 requestedBy，并使用 `selectedRun.events` 展示 TraceEvent 时间线。

`GET /api/runs/:id` 返回原始 Trace，包含 `trace.execution`、`trace.sandbox`、`trace.middleware`、`trace.policy`、`trace.worker` 和 `trace.events`。旧 Trace 没有这些字段时，`execution` / `sandbox` / `middleware` / `policy` / `worker` 归一为 `null`，`events` 归一为 `[]`。

`GET /api/plugins` 返回 Plugin Registry v1：capabilities、permissions、runtimePolicies 和 summary。`GET /api/policies` 返回权限与运行策略子集，供设置中心和后续审批 UI 复用。

`GET /api/artifact-preview` 返回 Previewer v1 响应：`artifact`、`preview`、`text`、`truncated`、`binary`。Workbench 右侧 Artifact detail 使用 `preview.kind` 渲染：

- `text`：展示截断文本内容和截断状态
- `image`：使用 Artifact URL 内嵌图片
- `pdf` / `office` / `binary` / `unsupported`：展示不能内嵌的原因、sandbox scope 和外部打开能力

旧的 `GET /api/artifact-content` 继续保留，作为只读文本预览兼容接口。

## 7. 当前交互闭环

### 7.1 创建 Agent

```text
输入需求
  -> POST /api/meta/create-agent
  -> 生成草案
  -> 右侧展示草案 Artifact
  -> Work 状态等待用户审核
```

### 7.2 安装 Agent

```text
选择 Meta-Agent run
  -> POST /api/meta/install-agent
  -> 安装到 agents/
  -> Agents 列表刷新
```

目标已存在时进入冲突态：

- 创建新版本
- 查看 diff 摘要
- 放弃安装

### 7.3 运行 Agent

```text
选择 Agent
  -> 输入 prompt
  -> POST /api/agent/run
  -> dry-run 或真实 provider 调用
  -> 写 Trace / Work / Message / Artifact
  -> 右侧切换到新 Run
```

## 8. 状态与空态

当前必须覆盖：

- API 加载中
- API 失败
- 静态预览模式
- 无 Run
- dry-run 无 Artifact
- 安装按钮不可用原因
- Agent 安装冲突
- settings 数据缺失

这些状态应该在 UI 中给出具体下一步，而不是只显示抽象错误。

## 9. 设计约束

- 工作台优先，避免 landing page 化。
- 信息密度适中，面向反复使用，而不是展示海报。
- 不用节点画布作为主路径。
- Artifact 和 Trace 是右侧上下文，不抢占对话主线。
- 设置中心展示 Agent 运行底座的继承关系。
- 中英文文案都要可读，但中文是默认体验。
