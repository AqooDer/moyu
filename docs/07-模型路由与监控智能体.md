# 07 - 模型路由与监控智能体

> 路由（Router）决定每次 LLM 调用用哪个模型；监控智能体（Monitor-Agent）异步分析历史并优化路由规则。
> 核心原则：**路由是热路径走规则，监控是冷路径用 LLM**（ADR-004）。
> 撰写日期：2026-05-20

---

## 1. 为什么要拆成 Router + Monitor-Agent

| 维度 | 如果"每次都让 LLM 决定用哪个模型" | Router(规则) + Monitor(LLM) |
| --- | --- | --- |
| 单次延迟 | +200ms~1s | ~0ms（查表） |
| 单次成本 | +一次 LLM 调用 | 0 |
| 决策稳定性 | 高方差 | 完全确定 |
| 适应性 | 实时 | 需等 Monitor 周期 |
| 可调试性 | 黑盒 | 规则可见、可手改 |

**结论**：让 LLM 做"分析"的事，让代码做"决策"的事。Monitor-Agent 周期性把分析结果转成规则。

## 2. Model Tier 抽象

Agent Manifest 不直接指定具体模型，而是指定一组**抽象 Tier**。具体 Tier→Model 的映射由 Workspace 配置维护，便于跟随模型迭代而不动 Manifest。

> ⚠ 本文不写具体模型名（如 `claude-opus-4-7`、`gpt-4o`），避免文档与现实模型版本绑定后过期。具体映射见 `apps/desktop` 启动时随版本下发的 `default-tier-mapping.yaml`，用户可覆写。

### 2.1 Tier 抽象定义

| Tier | 定位描述（不绑模型） | 典型成本量级 / 1M tokens | 典型用途 |
| --- | --- | --- | --- |
| `cheap-extraction` | 廉价、低延迟、结构化能力够用 | $ | 解析、分类、抽取、校验 |
| `balanced-writing` | 通用写作/指令跟随主力 | $$ | 一般问答、摘要、改写、章节正文 |
| `long-context` | 大上下文窗口优先 | $$ | 长文档阅读、跨文件合成 |
| `frontier-reasoning` | 顶级推理/复杂规划 | $$$ | 关键决策、复杂代码、深度分析 |
| `vision-capable` | 多模态（图像理解） | 视具体模型 | OCR 辅助、截图理解、图表解读 |

**好处**：
- 模型迭代不需要改 Manifest，只改 Tier→Model 映射。
- 多 Provider 可在同 Tier 内互为 fallback。
- 不同用户/Workspace 可自定义"省钱档"vs"高质档"映射。

### 2.2 Tier→Model 映射（Workspace 配置示例）

```yaml
# default-tier-mapping.yaml (随 App 版本下发，用户可覆写)
tier_mapping:
  cheap-extraction:
    - { provider: anthropic, model: "<最便宜的可用 Haiku>", weight: 1 }
    - { provider: openai, model: "<最便宜的可用 mini>", weight: 1 }
  balanced-writing:
    - { provider: anthropic, model: "<当前主力 Sonnet>", weight: 2 }
    - { provider: openai, model: "<当前主力 GPT>", weight: 1 }
  long-context:
    - { provider: anthropic, model: "<长上下文档位>", weight: 1 }
  frontier-reasoning:
    - { provider: anthropic, model: "<旗舰 Opus>", weight: 1 }
  vision-capable:
    - { provider: anthropic, model: "<具备视觉的型号>", weight: 1 }
```

具体模型名由 **`packages/providers` 内的注册表**维护，发新模型时只更新注册表 + tier-mapping 默认值，不动其他模块。

`weight` 用于同 Tier 内的概率路由（A/B 实验、成本平衡）。

## 3. Router 输入与输出

### 3.1 输入（Routing Context）
```ts
interface RoutingContext {
  // Step 上下文
  agent_id: string;
  agent_version: string;
  step_name: string;
  step_kind: 'llm' | 'skill_llm' | 'meta_agent';

  // 任务特征
  input_tokens_estimate: number;
  expected_output_tokens: number;
  has_attachments: boolean;
  language: string | null;            // 'zh' / 'en' / mixed
  requires_long_context: boolean;     // >32k

  // Manifest 声明
  allowed_tiers: Tier[];
  routing_overrides: Record<string, Tier> | undefined;

  // 运行时
  workspace_id: string;
  user_priority: 'auto' | 'cheap' | 'best';
  budget_remaining_usd: number;
  recent_provider_health: Record<string, 'ok' | 'degraded' | 'down'>;
}
```

### 3.2 输出
```ts
interface RoutingDecision {
  tier: Tier;
  provider: string;
  model: string;
  rule_id: string;                    // 命中的规则 id（用于审计）
  fallback_chain: { provider: string; model: string }[];
  notes: string[];                    // 决策说明（写入 Trace）
}
```

## 4. 路由策略层次（从内到外）

```
1. 显式覆盖（最高）
   Manifest.routing_overrides[step_name]  → 直接选 Tier
2. 用户偏好
   user_priority == 'cheap' → 取 allowed_tiers 中最低档
   user_priority == 'best'  → 取最高档
3. 规则引擎（核心）
   匹配 Routing Rules（见 §5），命中后给出 Tier
4. 默认
   allowed_tiers 的中位档
5. 同 Tier 内 Provider 选择
   按 weight 概率，剔除 health=down 的
6. Fallback Chain
   按 Tier→Model 映射顺序，依次降级 / 跨 Provider 重试
```

## 5. Routing Rules（规则引擎）

规则集存 SQLite（可手改、可由 Monitor-Agent 增删），结构：

```yaml
# routing_rules.yaml（也作为序列化格式）
rules:
  - id: r-001
    description: 长上下文优先 large
    when:
      input_tokens_estimate: { ">": 32000 }
    then:
      tier: large

  - id: r-002
    description: 标书章节写作必须 large
    when:
      agent_tags: { contains: "投标" }
      step_name: { in: [ "section_writer", "polish" ] }
    then:
      tier: large

  - id: r-003
    description: 解析/抽取类用 medium
    when:
      step_name: { matches: "^(extract|parse|classify)_.*" }
    then:
      tier: medium

  - id: r-004
    description: 预算告急强制降级
    when:
      budget_remaining_usd: { "<": 1.0 }
    then:
      tier_max: small               # 上限封顶

  - id: r-005
    description: Monitor 学习产物（示例）
    auto_generated: true
    source_run_ids: [r-2026-05-18-xxx, ...]
    when:
      agent_id: "7a1c4e9e-...-bidding"
      step_name: "parse_scoring_matrix"
    then:
      tier: medium                  # 从 large 降到 medium，质量未下降
```

### 规则求值
- 解释器纯 TS，时间复杂度 O(rules)。
- 多条命中：取**最先匹配 + 最严格**（如 `tier_max` 覆盖 `tier`）。
- 命中即停（短路）。

### 规则来源
| 来源 | 标记 | 修改方式 |
| --- | --- | --- |
| 平台内置 | `system: true` | 升级随版本 |
| 用户手写 | `manual: true` | UI 编辑器 |
| Monitor-Agent 建议 | `auto_generated: true` | 进待审核队列，用户点采纳后生效 |

## 6. Fallback 与重试

```
首选: tier=large, provider=anthropic, model=opus-4-7
   │
   ├── 调用超时 / 5xx
   ▼
fallback: tier=large, provider=openai, model=gpt-4.5
   │
   ├── 仍失败
   ▼
降级: tier=medium, provider=anthropic, model=sonnet-4-6
   │
   ├── 失败
   ▼
最终失败：Step.error = { code: 'provider_exhausted', retriable: false }
```

**关键约束**：
- 同 Tier 跨 Provider 重试不计入用户的"质量降级"统计；
- 跨 Tier 降级**必须写 Trace 高亮**（"原计划 large，实际 medium"），让 Monitor-Agent 评估对质量的影响。

## 7. 成本预算

| 层级 | 来源 | 触发动作 |
| --- | --- | --- |
| Workspace 月预算 | 用户设置 | 超额 → 全平台路由强制 `tier_max: small` |
| Agent 单 Run 预算 | Manifest | 超额 → Run fail (`quota`) |
| Step 预算 | 推断（Tier × 估算 tokens） | 预检：超 Run 剩余预算就降级 |

UI 在每次 Run 启动前展示**估算成本范围**（按 Tier 上下界），用户确认后再跑。

## 8. Monitor-Agent

### 8.1 定位
- 平台内置的"离线分析师"
- 用 LLM（绑定 `frontier` Tier，不走 Router）
- 输出 = **可执行的优化建议**（路由规则 patch / Manifest patch / 告警）

### 8.2 触发时机
- 定时：每天凌晨 3 点（用户睡觉时）
- 累积：自上次运行后新 Trace ≥ 100 条
- 手动：用户点"立即分析"

### 8.3 工作流
```
1. 采样
   抽样最近窗口的 Trace（默认 7 天，最多 500 条）
   按 Agent 分组

2. 计算指标（纯代码，喂给 LLM 当上下文）
   - 各 Step 的：p50/p95 latency、token 消耗、失败率、重试率
   - 同 Step 不同 Tier 的对比（如果有过 fallback）
   - 用户的"重跑率"（隐含质量信号）
   - 成本占比 Top N

3. LLM 分析
   Prompt 模板：
     "以下是 Agent X 最近 7 天的运行指标。请识别：
      1) 哪些 Step 的 Tier 过高（同 Step 在低 Tier 跑过也成功）；
      2) 哪些 Step 的失败率明显高于平均，可能配置错；
      3) 哪些重试模式建议改 Manifest（如调整 Skill 顺序）；
      4) 哪些预算异常占比。"
   要求模型按结构化 JSON 输出建议。

4. 生成 Patch
   - 路由规则建议 → routing_rules.yaml 的 add/remove
   - Manifest 建议 → JSON Patch
   - 每条建议带：
     · 类型（cost-reduce / quality-fix / failure-fix）
     · 预期影响（"预计每次 Run 省 30%"）
     · 证据（关联的 Run id 列表）
     · 风险（"可能影响质量，建议 A/B 一周"）

5. 入待审核队列
   UI 通知用户："Monitor 有 3 条新建议"

6. 用户决策
   - 一键采纳 → 写入 routing_rules / 触发 Agent bump 版本
   - 忽略 → 标记，30 天内不再提同类
   - A/B 试跑 → 平台自动给一半 Run 用新规则（仅自动化任务，用户交互任务不参与 A/B）
```

### 8.4 质量评估（重点也最难）

**问题**：LLM 输出"好不好"很难自动判断。

**解决路径**（按可用性递增）：

| 信号 | 实现 | 可靠度 |
| --- | --- | --- |
| 显式信号 | UI 提供"赞 / 踩 / 重跑" 按钮 | 高，但稀疏 |
| 隐式：重跑 | 用户对同 Task 立刻发起重跑 = 不满意 | 中 |
| 隐式：编辑产物 | 用户在 UI 内手改 artifact 的字符比例 | 中 |
| 自动评测 Skill | Recipe 自带"评分 Skill"（如：标书评分 Skill 检查目录是否覆盖评分点） | 高（领域内） |
| 模型自评（LLM-as-judge） | 用 large Tier 评估 small Tier 的输出 | 低-中（有偏） |

v0.x 先做"显式 + 重跑 + 自动评测 Skill"三件套，LLM-as-judge 谨慎使用。

### 8.5 反馈闭环图

```
┌─────────┐  跑业务  ┌─────────┐ 写  ┌──────────┐
│  User   │ ───────► │  Run    │ ──► │ Trace DB │
└────┬────┘          └─────────┘     └────┬─────┘
     │ 显式反馈                            │ 采样
     │ (👍/👎/重跑/编辑)                   ▼
     │                                ┌──────────────┐

     │                                       │ 建议

     │ 审核                            │  待审核队列  │
```

## 9. 与 Provider 健康监控

独立的、纯代码的健康检测，不需要 Monitor-Agent：

| 信号 | 阈值 | 状态 |
| --- | --- | --- |
| 过去 5 分钟 5xx 率 > 20% | | `degraded` |
| 过去 5 分钟全部失败 | | `down` |
| p95 延迟 > Provider 基线 ×3 | | `degraded` |

`degraded` → 在同 Tier 内降权（weight × 0.3）。
`down` → 从同 Tier 候选剔除，每 60s 健康检查恢复。

## 11. 给后续实现的 Checklist

- [ ] Tier→Model 映射做版本化（导出/分享）
- [ ] 路由规则编辑器有 dry-run（粘贴一个 Trace，看会命中哪条规则）
- [ ] Monitor 建议必须可解释（不可解释直接丢弃）
- [ ] A/B 试跑结果统计 90% 置信区间
- [ ] 给社区准备"规则模板包"（如"省钱套餐"、"高质量套餐"）
- [ ] 危险操作（如把所有 large 降到 small）必须二次确认
- [ ] Monitor-Agent 自己的 token 消耗也要在 UI 体现（透明）
