# 03 - 核心概念定义

> 本文定义 Moyu 当前仓库采用的核心词表。读架构、运行时、Workbench 或 Agent 文档前，先以这里为准。标注为“设计方向”的能力表示概念保留，但当前实现尚未完整落地。

## 1. 项目对象

### Workspace

Workspace 是一个本地 Moyu 项目目录，也是当前运行边界。它包含源码、`agents/`、`traces/`、`artifacts/`、Workbench 前端和本地配置。

当前仓库的 Workspace 根目录是项目根目录。运行命令默认从这里读取：

- `agents/`：已安装本地 Agent
- `traces/`：Run Trace，本地生成并被 `.gitignore` 忽略
- `artifacts/`：运行产物和 Workbench store，本地生成并被 `.gitignore` 忽略
- `moyu.config.json`：本地 Workspace 配置，被 `.gitignore` 忽略

### Agent

Agent 是一个可被发现、校验和运行的本地文件夹。当前约定是：

- 逻辑 ID：例如 `image-gen/prototype-v1`
- 物理目录：例如 `agents/image-gen__prototype-v1`
- 必备文件：`manifest.yaml`、`ui.yaml`、`README.md`
- 必备目录：`skills/`、`history/`

当前运行器只真正支持生图原型 Agent，但 Agent 文件夹契约已经用于 Meta-Agent 生成草案和安装。

### Meta-Agent

Meta-Agent 是“创建 Agent 的 Agent”。当前实现位于 `src/meta/`，能力是把自然语言需求转成可审查的 Agent 草案，写入 `artifacts/meta-agent-runs/<run_id>/`，通过校验后再安装到 `agents/`。

当前 Meta-Agent 是规则化脚手架生成器，不是完整 LLM 规划器。对话澄清、自动代码生成、逐文件审核和 sandbox dry-run 属于后续设计方向。

### Work

Work 是一次任务会话，面向用户体验。一个 Work 可以关联一个或多个 Run，也可以承载对话消息、产物和后续确认动作。

当前 Work 记录存储在 `artifacts/workbench/work-store.json`，用于 Workbench 左侧任务列表和中间对话恢复。

当前已落地 Work Manager v1 只读投影：

- `src/runtime/work-manager.ts` 会把 WorkStore、Run Trace、Plan 和 Step 聚合为 `WorkSummary`
- Work lifecycle 会从最新 Run 状态恢复，`succeeded` 会投影为 `completed`，`failed` / `cancelled` 会作为派生状态暴露
- Work progress 优先按 `RuntimeTrace.plan.steps` 计算，没有 Plan 时回退到 Trace Step
- Workbench `works` 和 `/api/works` 都可以读取 lifecycle、progress、currentRunId 和 runIds

当前 Work Manager v1 不负责队列、后台执行、取消、重试、暂停恢复或可写状态迁移。

### Run

Run 是一次 Agent 或 Meta-Agent 执行记录，面向运行时追踪。Run 记录包含：

- Agent ID / 版本
- Recipe ID
- 输入摘要
- 状态、耗时、dry-run 标记
- 模型角色解析结果
- Plan、Middleware、Policy、Execution Mode、Sandbox Filesystem、Artifact Delivery Manifest、Worker、TraceEvent、Step、Artifact、Knowledge write-back 与 notes

当前 Run Trace 写入 `traces/<run_id>/run.json`。

### Plan

Plan 是 Work 内可见的任务计划，描述本次运行准备做哪些步骤、步骤之间的依赖、当前状态和摘要。

当前已落地 Plan v1 骨架：

- Meta-Agent 和生图 Agent 在执行前生成静态 Plan
- Plan 写入 `RuntimeTrace.plan`
- Workbench `selectedRun.plan` 和 CLI `run show` 可以读取
- WorkStore 会写入 `kind: "plan"` 的对话消息，形成“用户请求 -> 计划 -> 总结”的消息流

当前 Plan v1 还不是完整动态编排器，不支持用户确认、修改、跳过或恢复执行。

### Middleware Pipeline

Middleware Pipeline 是 Run 内的上下文装配快照，用来说明附件、历史、知识和插件能力如何进入本次 Agent 上下文。

当前已落地 Middleware Pipeline v1：

- Meta-Agent 和生图 Agent 在执行前生成静态 pipeline
- Pipeline 写入 `RuntimeTrace.middleware`
- Workbench `selectedRun.middleware`、右侧 Context tab 和 CLI `run show` 可以读取
- 阶段包括 `attachment-intake`、`history-summary`、`knowledge-context`、`capability-injection`
- 每个阶段记录 state、capabilityIds、policyIds、inputSummary、outputSummary 和 sources

当前 v1 是可追踪的装配骨架，不执行真实文件解析、RAG 检索、动态插件代码或 MCP call。

### Policy Evaluation

Policy Evaluation 是每次 Run 的策略评估快照，用来说明本次运行实际装配了哪些 capability、请求了哪些 permission，以及这些权限当前是 allowed、review_required、blocked 还是 unknown。

当前已落地 Permission & Policy Gate v1：

- Meta-Agent 和生图 Agent 在执行前生成静态 policy evaluation
- Policy 写入 `RuntimeTrace.policy`
- Workbench `selectedRun.policy`、右侧 Context tab、`/api/runs/:id` 和 CLI `run show` 可以读取
- 检查项包括 capability、permission、MCP、model role、runtime capture 和 artifact write scope
- 评估结果来自 Plugin Registry、Agent manifest MCP 装配、Middleware capability/policy 和 Run 装配上下文

当前 v1 只做只读评估和 Trace 记录，不做真实阻断、审批弹窗、配额扣减、MCP call 或插件安装。

### Execution Mode

Execution Mode 是每次 Run 的执行模式快照，用来说明本次运行是 `dry_run`、`live` 还是未来的 `replay`，由哪个入口调度、写入哪个 queue、为什么跳过或启用外部调用，以及当前能力边界是什么。

当前已落地 Runtime Execution Modes v1：

- Meta-Agent 和生图 Agent 在执行前生成静态 execution mode
- Execution Mode 写入 `RuntimeTrace.execution`
- Workbench `selectedRun.execution`、右侧 Context tab、`/api/runs/:id` 和 CLI `run show` 可以读取
- 生图 Agent 会记录用户请求 dry-run、Provider 缺失 fallback dry-run，或 Provider 已配置的 live mode
- Meta-Agent 草案创建记录为 `dry_run`，直接持久化记录为 `live`
- 能力项记录 state、summary 和 sources，例如 inline worker、Provider call、Artifact registration 和 MCP assembly

当前 v1 只做只读快照和 Trace 记录，不实现真实执行模式切换、后台队列、取消、重试、暂停、恢复或 replay。

### Sandbox Filesystem

Sandbox Filesystem 是 Run 级文件边界快照，用来说明本次运行有哪些可写目录、实际产物根目录在哪里、Trace 写到哪里，以及当前没有实现哪些隔离能力。

当前已落地 Sandbox Filesystem v1：

- Meta-Agent 和生图 Agent 在生成 Plan 后创建沙盒目录快照
- `workspace` / `uploads` / `temp` 位于 `artifacts/sandboxes/<run_id>/`
- `outputs` 指向本次运行实际产物目录，例如 `artifacts/meta-agent-runs/<run_id>` 或 `artifacts/agent-runs/<agent>/<run_id>`
- `traces` 指向 `traces/<run_id>`
- Sandbox 写入 `RuntimeTrace.sandbox`
- Workbench `selectedRun.sandbox`、右侧 Context tab、`/api/runs/:id` 和 CLI `run show` 可以读取

当前 v1 不是进程隔离，不提供 chroot、Docker、worker sandbox、上传 UI、删除/下载权限、路径审批或 MCP 文件访问执行。

### Step

Step 是 Run 内的最小可观察执行单元。当前类型包括：

- `llm`
- `tool`
- `skill`
- `agent_call`
- `control`
- `user_checkpoint`

当前实现主要使用 `skill` 和 `tool`，用于生图 Agent 运行、Meta-Agent 持久化和校验。

### Artifact

Artifact 是 Run 产生的可审查文件，不是任意临时日志。当前 Artifact 记录包含：

- `id`
- `runId`
- `producerStepId`
- `type`
- `role`
- `name`
- 绝对路径
- 文件大小
- `sha256`
- 创建时间

Workbench 和 CLI 可以列出、查看、打开 Artifact。

### Artifact Delivery Manifest

Artifact Delivery Manifest 是 Run 的交付清单，用来说明本次最终向用户交付了哪些 Artifact、哪个是主产物、总大小、可内嵌预览/外部打开数量，以及当前交付能力限制。

当前已落地 Artifact Delivery Manifest v1：

- Meta-Agent 和生图 Agent 会在 Trace 写入前生成静态 delivery manifest
- Delivery 写入 `RuntimeTrace.delivery`
- Workbench `selectedRun.delivery`、右侧 Artifact 面板、`/api/runs/:id` 和 CLI `run show` 可以读取
- dry-run 或无输出运行会写入 `state: "empty"` 的 delivery，失败收口会写入 `failed` 或 `partial`
- Delivery 基于已有 Artifact 和 Previewer v1 元数据生成，不额外复制文件

当前 v1 只做只读交付摘要，不实现 zip 打包下载、下载权限审批、删除 UI、Artifact 版本图、diff 编辑器或采纳工作流。

## 2. 能力对象

### Skill

Skill 是 Agent 目录内的一段能力实现或能力声明。当前生图 Agent 使用：

```text
skills/image_gen_via_relay/
├── skill.yaml
└── index.ts
```

当前运行器没有动态加载任意 Skill 代码；生图调用由 `src/agent/run.ts` 的原型运行器完成。受控生成 Skill、静态检查和沙箱试跑是后续设计方向。

### Tool

Tool 是平台内置动作，例如读写文件、打开产物、安装 Agent 草案、查询 Trace。当前 Tool 主要以 CLI 命令和 Workbench API 的形式出现。

### MCP

MCP 是外部工具协议，也是 Agent 的可选能力装配。当前 Agent `manifest.yaml` 可以通过 `mcp_servers` 声明所需 MCP Server；registry、validator、Run Trace 和 Workbench 会保留这份装配快照。

当前仍没有启动真实 MCP Server，也没有实现 MCP Client 调用、server lifecycle 或权限审批 UI。问数 Agent 通过 MCP 取数等能力属于后续执行器任务。

### Model Role

Model Role 是“用途角色”，不是具体模型名。当前内置角色包括：

- `conversation-primary`
- `planning-reasoning`
- `knowledge-embedding`
- `image-generation`

解析优先级：

1. 内置默认值
2. `moyu.config.json` 的 `model_roles`
3. Agent `manifest.yaml` 的 `routing.model_roles`
4. 运行时环境变量，例如 `MOYU_IMAGE_PROVIDER_MODEL`

Run Trace 会记录最终命中的 role、provider、model、来源和 fallback reason。

### Knowledge Base

Knowledge Base 是 Workspace 级知识集合配置。当前实现支持读取和展示：

- 集合 ID、标题、状态
- embedding role
- chunk strategy
- connected agents
- sources
- write-back policy 和允许回流的 Artifact 类型

真实切片、向量索引、召回查询尚未实现。Artifact write-back 当前记录审核后的回流事件，但不做真实索引。

## 3. UI 与数据对象

### Workbench

Workbench 是本地三栏工作台：

- 左侧：Work、Agent、设置入口
- 中间：任务会话与操作区
- 右侧：Artifact、Trace、详情和设置检查器

Workbench 通过本地服务读取真实 API。导出的 `artifacts/workbench-data/workbench.json` 只用于人工检查，不再作为页面兜底数据。

### Settings

Settings 是 Workspace 运行底座的可视化控制面板，不是杂项配置页。当前包含：

- Overview
- Models
- Agent Context
- Knowledge
- Skills
- Tools
- MCP
- Runtime

当前 Settings 主要可读，不提供保存编辑。

### Trace

Trace 是可追踪运行证据的总称。当前具体落地是 JSON 文件：

```text
traces/<run_id>/run.json
```

Workbench 右侧 Trace 面板和 CLI `run show` 都从这里读取。

## 4. 目标架构概念

以下概念属于目标架构 / 设计方向，用来约束后续 P0-P6 路线，不代表当前已经完整实现。

### Framework Host / Harness

Framework Host / Harness 是所有 Agent 的共同运行底座。它负责对话编排、任务计划、运行状态、沙盒文件系统、产物、插件、权限、异步执行、Trace 和设置策略。

后续 Meta-Agent 和业务 Agent 都应运行在同一个 Framework Host 上，避免每类 Agent 各自实现文件、插件、权限和对话状态。

### Plan 目标形态

目标形态中的 Plan 是 Work 内可确认、可调整的任务计划。它会描述阶段、步骤、依赖、确认点、失败恢复点和验收方式。

当前 v1 只落地静态计划和状态追踪；Plan 与 Run 的完整分离、用户确认和失败恢复仍是后续 P1/P3 工作。

### Sandbox Filesystem / SandboxFile

目标形态中的 Sandbox Filesystem 会从当前 Run 级目录快照演进为 Work / Run 级隔离文件空间，结构包括：

- `workspace/`：任务工作区
- `uploads/`：用户上传文件
- `outputs/`：Agent 生成产物
- `temp/`：执行过程临时文件

SandboxFile 仍是后续设计方向。它会作为沙盒内文件的登记对象，记录路径、来源、类型、大小、摘要、权限和预览状态。后续文件预览、Artifact、插件和知识入库都应从 SandboxFile 获取文件边界。

### Plugin

Plugin 是可扩展能力的统一注册对象。目标上不只包括 Skill / Tool / MCP，也包括 Previewer、Parser、Exporter、Middleware 和 Policy 扩展。

Plugin 必须声明能力、入口、版本、权限、适用 Agent / Workspace 范围和安装验证方式。

当前 v1 已落地只读内置 registry：`src/plugins/registry.ts` 统一声明 Skill、Tool、MCP、Previewer、Middleware、权限边界和运行策略，并通过 Settings / `/api/plugins` / `/api/policies` 暴露。它还不是插件安装器，不热加载外部代码，也不做逐次审批拦截。

### Previewer

Previewer 是文件预览插件，负责把 SandboxFile 或 Artifact 转成 Workbench 可安全展示的视图。

目标格式包括 Markdown、文本、JSON、图片、PDF、DOC/DOCX、HTML、CSV/Excel、PPT/PPTX 和日志。HTML 等主动内容必须走安全预览边界。

### Middleware

Middleware 是对话和运行过程中的可组合处理环节。典型能力包括附件解析、历史摘要、RAG 注入、动态工具注入、模型上下文压缩和输出审查。

Middleware 属于框架层能力，不应写死在某个 Agent 的 prompt 或运行器里。

当前 v1 已把 Middleware 作为 Runtime Trace 的 `middleware` 快照和 Plugin Registry 的 `context-pack-middleware` 声明落地，但还没有可配置 pipeline 编排器。

### Policy

Policy 是权限、审批和运行边界声明。目标覆盖文件读写、命令执行、网络访问、MCP 调用、插件安装、子智能体调用、模型配额和敏感路径。

Policy 的结果必须写入 Trace，用户确认点必须能在 Work 中恢复。

当前 v1 的 Policy 是 registry permission 声明，用于展示和装配依据；真实审批、阻断执行和审批结果写 Trace 是后续 P1/P3 工作。

### SubAgent

SubAgent 是由主 Agent 编排的子智能体运行。它拥有独立上下文、child run、权限边界和产物回传机制。

SubAgent 用于复杂任务拆分和上下文隔离，不用于绕过主 Work 的权限与 Trace。

### Async Worker

Async Worker 是长任务执行机制。目标支持分钟级/小时级任务的后台执行、取消、重试、恢复、流式事件和失败续跑。

所有 Async Worker 任务仍然归属 Work / Run / Step，不产生游离于主任务之外的隐式状态。

当前已落地 Async Worker v1 骨架：

- Meta-Agent 创建 Agent 和生图 Agent 运行都会创建 `WorkerJobRecord`
- 当前 worker 模式是 `inline`，用于把同步入口包进可追踪 worker envelope
- Worker 写入 `RuntimeTrace.worker`
- Workbench `selectedRun.worker`、右侧 Context tab、`/api/runs/:id` 和 CLI `run show` 可以读取

当前 v1 不实现跨进程后台队列、并发调度、真实取消、重试、暂停恢复或 worker sandbox。

### TraceEvent

TraceEvent 是目标事件流的最小记录单元，用于驱动 UI、回放运行、排查问题和统计成本。

当前已落地 TraceEvent v1 骨架：

- 事件写入 `RuntimeTrace.events`
- 已记录 execution mode selected、worker queued/started/finished、run state、plan、middleware、policy、step、artifact、trace written 和 note
- Workbench `selectedRun.events`、右侧 Context tab、`/api/runs/:id` 和 CLI `run show` 可以读取
- 旧 Trace 没有事件时读取为 `events: []`

后续 ToolCall、SkillCall、McpCall、AgentCall、Policy 审批、replay 和用户插话都应继续扩展为事件。

## 5. 当前不混用的词

- Task：历史文档中曾与 Work 混用；当前面向用户统一使用 Work，面向运行时使用 Run。
- Recipe：当前作为 Agent manifest 的 `recipe_ref` 和 Meta-Agent `recipeId` 保留，但没有独立 Recipe 引擎。
- Monitor-Agent：设计方向，当前未实现。
- Sandbox：当前已落地 Run 级文件系统快照；仍没有 worker_threads、isolated-vm、chroot 或 Docker 执行隔离。
- Router：当前只有模型角色解析和生图模型覆盖，不是完整动态路由系统。

## 6. 落地约束

- 文档描述当前实现时，必须能映射到 `src/`、`agents/`、`ui/workbench/` 或配置文件。
- 未来能力必须标注“设计方向”或“未实现”。
- 术语变化需要同步 `04`、`05`、`06`、`14` 和 README 中的相关表述。
