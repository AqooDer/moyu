## 1. 运行时总览

```
┌──────────────────── Orchestration Engine ─────────────────────┐
│                                                                │
│  Task ─► Run (state machine) ─► Step* (DAG / Sequence / ReAct)│
│                │                       │                       │
│                ▼                       ▼                       │
│         Trace Recorder            Step Executor                │
│                                        │                       │
│         ┌──────────────────────────────┼───────────────────┐  │
│         ▼                              ▼                   ▼  │
│   Skill Invoker               Tool Invoker          LLM Invoker│
│         │                              │                   │  │
└─────────┼──────────────────────────────┼───────────────────┼──┘
          ▼                              ▼                   ▼
     Sandbox Pool                  Tool Registry        Model Router
   (L0 / L1 / L2)                  (含 MCP Client)     (Provider)
```

## 2. 三个核心对象：Task / Run / Step

### 2.1 Task
**定义**：用户的一次执行意图。一个 Task 可以跑出多个 Run（重试、续跑）。

```ts
interface Task {
  id: string;
  agent_id: string;
  agent_version: string;
  inputs: unknown;             // 符合 inputs_schema
  created_at: string;
  created_by: 'user' | 'meta-agent' | 'monitor-agent';
  current_run_id: string | null;
  status: 'idle' | 'running' | 'succeeded' | 'failed' | 'cancelled';
  retention_policy: 'forever' | 'keep_30d' | 'delete_on_complete';
}
```

### 2.2 Run
**定义**：Task 的一次具体执行实例。

```ts
interface Run {
  id: string;
  task_id: string;
  started_at: string;
  ended_at: string | null;
  state: 'queued' | 'preparing' | 'running'
       | 'paused' | 'cancelling'
       | 'succeeded' | 'failed' | 'cancelled';
  reason: string | null;       // 失败/取消原因
  cost: { tokens: number; usd: number };
  artifacts: Artifact[];       // 产出文件
  trace_id: string;
  parent_run_id: string | null; // 重试时指向上一次
}
```

### 2.3 Step
**定义**：Run 内部的原子操作。

```ts
type StepKind = 'llm' | 'tool' | 'skill' | 'control';

interface Step {
  id: string;
  run_id: string;
  parent_step_id: string | null;   // 嵌套（Skill 内部还有 LLM Step）
  kind: StepKind;
  name: string;                     // 'extract_pdf' / 'call_claude' 等
  inputs: unknown;
  outputs: unknown | null;
  state: 'pending' | 'running' | 'succeeded' | 'failed' | 'retrying';
  started_at: string | null;
  ended_at: string | null;
  attempt: number;
  sandbox_level: 'L0' | 'L1' | 'L2';
  resource_usage: { cpu_ms: number; mem_peak_mb: number; tokens: number };
  error: { code: string; message: string; retriable: boolean } | null;
}
```

### 2.4 Trace
Trace 是 Run 的"录像带"——所有 Step 时序 + IO + 错误，按 OpenTelemetry-like 结构存 SQLite + 大对象 blob 文件。

> **完整字段、表结构、blob 命名、保留策略、脱敏规则、schema 演进规则**全部见 `12-Trace数据模型.md`。本文不再重复定义。
>
> 关键约束：**Trace schema 在 v0.1 一开始就要敲定**（字段名 / 类型 / 摘要 vs blob 切分），后续可加字段、不可删字段、不可改语义。返工成本最高的是 schema 变更。

UI 提供：
- 时间轴视图(甘特图)
- 树形视图(嵌套 Step)
- 单 Step 详情(input/output diff)
- **回放**：重新跑 Step N 之后的所有 Step(用于调试 Skill)

## 3. 三种工作流模式

Agent 的 `workflow.kind` 决定编排引擎用哪种执行模式：

### 3.1 `sequence`（线性）
```
Step A ─► Step B ─► Step C
```
最简单、最常用。失败 = 终止。

### 3.2 `dag`（有向无环图）
```
       ┌─► B ─┐
A ──►──┤      ├──► D
       └─► C ─┘
```
- 并行：B、C 可同时跑；
- 汇聚：D 等 B、C 都成功；
- `fanout: per_section` 等动态并行（如"按章节并行写"）。

### 3.3 `react`（推理 + 行动循环）
```
loop:
  LLM 决策（thought + action）
  执行 action（tool 调用）
  observation 入上下文
until LLM 输出 final_answer 或 达到 max_loops
```
- 适合开放式问题（"帮我研究下 X"）；
- max_loops 是硬上限（防止死循环）。

**默认推荐**：业务 Agent 优先 `dag`（可控），交互 Agent 用 `react`。

## 4. Step 执行模型

每个 Step 进入 Step Executor 后的流程：

```
1. 准入检查（Quota / Capability / Sandbox 可用性）
   失败 → 直接 fail (retriable=false)

2. 选择 Sandbox 实例
   L0 → 主进程直接调
   L1 → 从 worker pool 拿一个 worker
   L2 → docker run --rm 启一个容器（按 image 缓存）

3. 物料注入（Inputs + Capability + Working Memory 切片）

4. 执行
   - LLM Step: 走 Router 选 model → Provider 调用
   - Tool Step: 走 Registry 找到实现 → 调用（含 MCP）
   - Skill Step: 在 Sandbox 内跑 Skill 脚本入口函数

5. 资源用量统计（CPU/Mem/Token）

6. 输出校验（如有 schema）

7. 写 Trace + Working Memory

8. 成功 → 触发后继 Step；失败 → 重试策略
```

## 5. 沙箱（Sandbox）

### 5.1 三级模型

| 级别 | 实现 | 启动延迟 | 隔离强度 | 适合 |
| --- | --- | --- | --- | --- |
| **L0** | 同 Core 进程 | 0 | 无 | Provider 直调（LLM API），完全无用户代码 |
| **L1** | `worker_threads` + `isolated-vm` | ~10ms（worker 预热后） | 高（V8 Isolate，无 Node API） | 用户/Meta 生成的 Skill 脚本、JSON 处理 |
| **L2** | Docker 容器 | ~1s（image 缓存后） | 完全 OS 级 | 需要文件系统、外部 CLI、网络的 Skill |

### 5.2 L0 — 同进程
- 仅 Provider 调用走 L0：因为 Provider SDK 本身经过审计，没必要隔离。
- 入口函数签名固定，参数走 Zod 校验。
- **唯一的隔离手段**：调用超时（`AbortSignal`）+ Token 上限。

### 5.3 L1 — worker_threads + isolated-vm

**为什么不直接用 `worker_threads`？**
- `worker_threads` 跑的还是完整 Node API（fs/net 都有）。
- 要安全跑 Skill 脚本，必须再套一层 V8 Isolate。

**结构**：
```
Core (主线程)
  │ postMessage(skill_request)
  ▼
Worker (Node thread)
  │ 创建 isolated-vm Isolate
  │   • 内存上限：128MB
  │   • CPU 时间：5s
  │   • 无 require、无 process、无 fs
  ▼
Isolate
  │ 暴露给用户脚本的 API（通过 ivm.Reference 注入）：
  │   • `host.fs.read(path)`       —— 走能力授权
  │   • `host.fs.write(path, buf)` —— 同上
  │   • `host.llm.call({...})`     —— 转回 Core 走 Router
  │   • `host.tool.call(name, args)` —— 同上
  │   • `console.log` —— 重定向到 Trace
  ▼
执行 Skill 入口函数（async function run(inputs, ctx))
```

**关键设计**：
- **Host API 是同步桥接的异步**：Isolate 调 `host.fs.read` → 走 ivm 同步通道 → Worker 异步执行 → 结果回传。
- **每次 Skill 调用一个新 Isolate**：避免状态污染；Isolate 创建/销毁开销 ~3ms。
- **Worker 池预热**：启动时预创建 N 个 worker（N = CPU 核数 / 2，最少 2）。

### 5.4 L2 — Docker

**何时启用**：
- Skill 声明 `requires: docker` 或
- `capabilities.net_domains` 非空 或
- 需要调用本地 CLI 工具（pandoc、ffmpeg、libreoffice）。

**实现要点**：
- 镜像基础：`node:20-alpine` + 预装常用 CLI 的"标准镜像"，用户也可自带镜像。
- 容器命名：`moyu-l2-{run_id}-{step_id}`，便于追踪。
- 网络：默认 `--network=none`，按白名单加 `--add-host`。
- 文件挂载：`workspace_path` 只读 + 容器内 `/out` 可写并回拷。
- 资源：`--cpus`、`--memory`、`--pids-limit`。
- 超时：外层 `AbortController` + 容器层 `--stop-timeout`。

**用户没装 Docker 时**：
- UI 显式提示 + 给出安装链接；
- 不偷偷降级到 L1（安全模型必须明确）。

## 6. 资源配额（Quota）

Quota 在三处生效（**多层防护**）：

| 维度 | Step 级 | Run 级 | Agent 级 |
| --- | --- | --- | --- |
| Wall time | ✅ AbortSignal | ✅ Watcher | ✅ Manifest 默认 |
| CPU time | L1/L2 | — | — |
| Memory peak | L1/L2 | — | — |
| Tokens | LLM 调用层拦截 | Run 总和 | Manifest |
| Cost (USD) | — | ✅ | ✅ |

**超额行为**：Step 抛 `QuotaExceededError(retriable=false)`，Run 进入 `failed` 并写明哪条 quota 触发。

## 7. 能力授权（Capabilities）

Manifest 中 `sandbox.capabilities` 声明 Agent 允许触达的资源：

```yaml
capabilities:
  fs_read: ["${workspace}/inputs/**"]
  fs_write: ["${workspace}/outputs/**"]
  net_domains: ["api.openai.com", "*.anthropic.com"]
```

- 路径用 glob，运行时变量 `${workspace}`、`${tempdir}` 自动展开。
- 域名走 DNS 解析白名单（L2 Docker 用 iptables/`--add-host` 强制）。
- **越权访问不是"拒绝并继续"，而是 Step fail**——让 LLM 学会要求授权。

**升级授权**：
- Agent 第一次试图越权 → Run 暂停，UI 弹出"是否授予 X 能力"。
- 用户授权 → 自动 patch Manifest（bump minor 版本），继续执行。

## 8. 进程间通信（IPC）

```
Renderer ──IPC──► Main ──HTTP/JSON-RPC──► Core ──msgpack/stdio──► Sandbox
   |                                            ▲                    │
   |                                            └─────────回包─────────┘
   └── 长任务用 SSE / WebSocket（同 Main 转发）
```

| 通道 | 协议 | 选型理由 |
| --- | --- | --- |
| Renderer ↔ Main | Electron contextBridge IPC | 安全（无 nodeIntegration） |
| Main ↔ Core | HTTP + JSON-RPC（loopback） | Core 可独立部署；调试方便 |
| Main → Renderer 推送 | EventSource (SSE) | Run 进度流式推送 |
| Core ↔ Sandbox L1 | worker.postMessage（结构化克隆） | Node 原生 |
| Core ↔ Sandbox L2 | stdin/stdout + msgpack | 进程边界友好 |

**协议版本**：所有跨进程协议都带 `protocol_version` 字段，便于平滑升级。

## 9. 暂停 / 续跑 / 取消

| 操作 | 行为 |
| --- | --- |
| **暂停** | 等待当前 Step 完成 → Run 进入 `paused`；下游 Step 不再调度；不释放 Working Memory |
| **续跑** | 从最后一个未完成 Step 调度；如果 Working Memory 已被换出（超时清理），自动从 Episodic 重建 |
| **取消** | 立即向 Sandbox 发 SIGTERM；超时强杀；Step 状态置 `cancelled` |
| **重试 Run** | 复用 Inputs，创建新 Run（`parent_run_id` 指向原 Run）；可选择"完全重跑"或"从失败 Step 续跑" |
| **回放（Replay）** | 用历史 Trace 的 LLM 调用响应做 mock，重跑下游 Step —— 用于调试 Skill |

**关键约束**：
- LLM 调用是不幂等的，重跑会重新计费。UI 显式提示。
- Tool 调用如果有副作用（如发邮件），Manifest 必须声明 `idempotency_key`，引擎按 key 去重。

## 10. 错误处理与重试

### 10.1 错误分类
```ts
type ErrorCategory =
  | 'user_input'      // 输入不符合 schema（不可重试）
  | 'config'          // Manifest 错误（不可重试）
  | 'provider'        // LLM API 故障（可重试，退避）
  | 'tool'            // 工具失败（按 tool 声明决定）
  | 'sandbox'         // 沙箱崩溃（重试一次后转 L 升级建议）
  | 'quota'           // 超额（不可重试）
  | 'internal';       // 平台 bug（不可重试，上报）
```

### 10.2 重试策略
| 类别 | 策略 | 最大次数 |
| --- | --- | --- |
| `provider` | 指数退避：1s, 4s, 16s + jitter | 3 |
| `tool` (idempotent) | 固定 2s | 2 |
| `tool` (non-idempotent) | 不重试 | 0 |
| `sandbox` | 立即（换一个 worker） | 1 |
| 其他 | 不重试 | 0 |

### 10.3 失败传播
- DAG 模式：失败节点不阻断"独立分支"；汇聚节点等所有上游结束（成功/失败）再决定。
- Sequence 模式：失败即终止。
- ReAct 模式：失败的 action 作为 observation 喂回 LLM，让其自决策。

## 11. 调度与并发

### 11.1 Run 级
- 默认全局并发 = `min(cpu_cores, 4)`；
- 用户可在设置里改；
- 超出排队（FIFO）。

### 11.2 Step 级（同 Run 内）
- DAG 节点并行度 = `min(node.fanout || 1, agent.max_parallel || 4)`；
- 共享 Sandbox 池资源，超额节点排队。

### 11.3 优先级
- Meta-Agent 的 DRY_RUN > Monitor-Agent > 用户 Task
- 同优先级 FIFO

- [x] Renderer 关闭 nodeIntegration、开启 contextIsolation
