# 06 - 运行时与数据模型

> 本文合并原 Trace 数据模型、Artifact 契约、运行时与沙箱设计中当前已经落地的部分。当前实现以 `src/runtime/`、`src/settings/` 和 `src/agent/run.ts` 为准。

## 1. 当前运行时边界

当前 Moyu runtime 是本地 JSON 文件运行时：

- Run Trace 写入 `traces/<run_id>/run.json`
- Artifact 是本地文件，并在 Trace 中登记元数据
- Work / Message 写入 `artifacts/workbench/work-store.json`
- Workbench 数据由 `src/runtime/workbench-data.ts` 聚合

当前没有通用调度器、队列、SQLite、sandbox worker 或 Docker 隔离。

## 2. Run

Run 是一次执行记录。当前类型定义在 `src/runtime/types.ts`：

```ts
interface RunRecord {
  id: string;
  workId?: string | null;
  agentId: string;
  agentVersion: string;
  recipeId: string | null;
  state: "queued" | "running" | "succeeded" | "failed" | "cancelled";
  dryRun: boolean;
  startedAt: string;
  endedAt: string | null;
  durationMs: number | null;
  input: Record<string, unknown>;
  reason: string | null;
  modelRoles: ModelRoleResolution[];
  mcpServers: McpServerResolution[];
}
```

当前 Run 由 `RuntimeStore.createRun` 创建。Agent run、Meta-Agent create run 都使用同一套 Trace 格式。

## 3. Step

Step 是 Run 内的可观察阶段。

```ts
type StepKind = "llm" | "tool" | "skill" | "agent_call" | "control" | "user_checkpoint";
type StepState = "pending" | "running" | "succeeded" | "failed" | "skipped";
```

当前使用方式：

- 生图 Agent：`step-image-gen`
- Meta-Agent：`intake`、`spec-draft`、`persist`、`validate`、`register-artifacts`

Step 记录输入摘要、输出摘要、错误信息和耗时。

## 4. Execution Runtime Step Runner

`src/runtime/step-runner.ts` 是当前 Execution Runtime 的最小 step 执行包装器。它建立在 `RuntimeStore` 之上，不改变 Trace schema。

当前职责：

- `runRuntimeStep` 创建 Step，并执行调用方传入的函数
- Step 返回后统一写入 `succeeded` / `skipped` / `failed`
- 异常时先写入 failed Step 和 `error.code` / `error.message`，再把异常继续抛给上层
- `finishRuntimeStep` 复用 `RuntimeStore.finishStep`，因此会同步对应 Plan Step 状态
- 执行函数可以拿到 `step` 和 `runtime`，用于登记 Artifact 或追加 notes

当前接入点：

- 生图 Agent 的 `step-image-gen`
- Meta-Agent 创建 Agent 的 `intake`、`spec-draft`、`persist`、`validate`、`register-artifacts`

### Failed Run Finalizer v1

`src/runtime/run-finalizer.ts` 是当前失败收口器。它处理的边界是：执行入口已经创建 `RuntimeStore` 和 Plan，后续 step 或入口逻辑抛出异常。

当前职责：

- 把原始异常归一化为 `error.code` / `error.message`
- 追加 `Run failed: <code>: <message>` note
- 把 `run.state` 和 `plan.state` 写为 `failed`
- 写出 `traces/<run_id>/run.json`
- 写入 WorkStore 对话消息：用户请求 -> 计划 -> 失败总结
- 失败收口后，入口继续向 CLI / API 抛出原始异常

当前接入点：

- 生图 Agent provider / skill 异常
- Meta-Agent 创建 Agent 的执行异常，例如持久化目标目录冲突

当前限制：

- 不是 DAG / workflow engine
- 不负责队列、后台 worker、取消、重试或暂停恢复
- 不执行真实 MCP call
- 不在本层决定 run 最终状态或 Trace 落盘时机
- 不处理 Runtime / Plan 创建之前的配置解析失败

## 5. Artifact

Artifact 是 Run 产生的可审查文件。

```ts
interface ArtifactRecord {
  id: string;
  runId: string;
  producerStepId: string;
  type: string;
  role: "primary" | "intermediate" | "report" | "log";
  name: string;
  path: string;
  sizeBytes: number;
  sha256: string;
  createdAt: string;
}
```

当前 Artifact 来源：

- 生图输出 PNG
- dry-run summary / README
- Meta-Agent 生成的 manifest、ui、README、Skill、history、验证记录、draft record

CLI：

```bash
npm run dev -- artifact list
npm run dev -- artifact list --run <run_id>
npm run dev -- artifact show <artifact_id>
npm run dev -- artifact open <artifact_id>
```

Workbench 右侧可以展示 Artifact 列表，并读取文本产物内容。

## 6. RuntimeTrace

Trace 文件结构：

```ts
interface RuntimeTrace {
  schemaVersion: 1;
  run: RunRecord;
  plan: PlanRecord | null;
  steps: StepRecord[];
  artifacts: ArtifactRecord[];
  knowledgeWriteBacks: KnowledgeWriteBackRecord[];
  notes: string[];
}
```

Plan v1 已进入 Trace，但仍是 plan-first 骨架，不是完整动态编排器：

```ts
interface PlanRecord {
  id: string;
  runId: string;
  workId: string;
  title: string;
  state: "drafted" | "running" | "succeeded" | "failed" | "cancelled";
  steps: PlanStepRecord[];
  createdAt: string;
  updatedAt: string;
}

interface PlanStepRecord {
  id: string;
  title: string;
  kind: StepKind;
  state: StepState;
  dependsOn: string[];
  summary: string;
}
```

当前规则：

- Meta-Agent 和生图 Agent 会在执行前生成静态 Plan。
- `RuntimeStore` 会在对应 Step 开始和结束时同步 Plan Step 状态。
- 旧 Trace 不含 `plan` 时读取为 `plan: null`。
- CLI `run show <run_id>` 会打印 Plan 摘要。
- 本阶段不支持用户确认、修改、跳过 Plan，也不执行真实 MCP call。

写入位置：

```text
traces/<run_id>/run.json
```

查询入口：

```bash
npm run dev -- run list
npm run dev -- run show <run_id>
```

Workbench API：

```text
GET /api/runs/:id
POST /api/run/open-trace
```

## 7. Work / Message

Work 是用户任务会话，Message 是会话消息。

当前存储：

```text
artifacts/workbench/work-store.json
```

结构：

```ts
interface WorkStoreFile {
  schemaVersion: 1;
  updatedAt: string;
  works: WorkRecord[];
  messages: ConversationMessage[];
}
```

状态：

- `active`
- `waiting_user`
- `running`
- `completed`
- `archived`

当前用途：

- Workbench 左侧任务列表
- 中间对话流恢复
- plan-first 对话消息：用户请求 -> 计划 -> 总结
- Meta-Agent 创建草案后的等待用户安装状态
- Agent run 完成后的 summary message

## 8. Work Manager v1

Work Manager v1 是只读生命周期投影层，代码位于 `src/runtime/work-manager.ts`。它不改变 WorkStore schema，而是把 WorkStore 和 Trace 聚合成 `WorkSummary`：

```ts
interface WorkSummary {
  id: string;
  title: string;
  state: "active" | "waiting_user" | "running" | "completed" | "archived" | "failed" | "cancelled" | "unknown";
  storedState: WorkState | null;
  runIds: string[];
  currentRunId: string | null;
  lifecycle: WorkLifecycle;
  progress: WorkProgress;
}
```

生命周期来源：

- `run_trace`：WorkStore 关联的最新 Run Trace
- `work_store`：只有 WorkStore 记录，暂时没有可读 Trace
- `fallback_trace`：Trace 存在，但没有 WorkStore 记录

状态投影规则：

- `archived` 的 WorkStore 状态优先保留
- Run `failed` / `cancelled` 分别投影为 `failed` / `cancelled`
- Run `queued` / `running` 投影为 `running`
- WorkStore `waiting_user` 优先表示等待用户动作
- Run `succeeded` 投影为 `completed`
- 其他情况回退到 WorkStore 状态或 `unknown`

进度计算：

- 优先读取 `RuntimeTrace.plan.steps`
- 没有 Plan 时回退读取 `RuntimeTrace.steps`
- `succeeded` 和 `skipped` 都计入 completedSteps
- 没有步骤时，`succeeded` 视为 100%，`running` / `queued` 视为 50%，其他为 0%

暴露入口：

- Workbench `works` 字段
- `GET /api/works?state=<state>`

当前限制：

- 不负责队列、后台 worker、取消、重试或真实恢复执行
- 不提供可写 Work 状态迁移 API
- 不做跨进程并发调度或事务保证

## 9. Model Role Resolution

模型角色解析用于避免把具体模型写死进业务逻辑。

来源优先级：

1. 内置默认值
2. `moyu.config.json`
3. Agent `manifest.yaml`
4. 运行时环境变量

Trace 记录：

```ts
interface ModelRoleResolution {
  roleId: string;
  provider: string;
  model: string;
  source: "builtin_default" | "workspace_config" | "agent_manifest" | "runtime_env";
  fallbackReason: string | null;
  providerEndpoint?: string | null;
}
```

生图角色特殊规则：

- 缺少图片中转配置时，Run 可 dry-run 或跳过 provider，并记录 `missing_image_provider_config`
- 设置 `MOYU_IMAGE_PROVIDER_MODEL` 时覆盖 `image-generation` 模型，并记录 `env_model_override`

## 9. MCP Server Resolution

MCP 装配用于记录 Agent 运行时可用的外部工具协议能力。

来源：

1. Agent `manifest.yaml` 的 `mcp_servers`

Trace 记录：

```ts
interface McpServerResolution {
  id: string;
  transport: string | null;
  state: string | null;
  description: string | null;
  permissions: string[];
  source: "agent_manifest";
}
```

当前运行器只记录 MCP 装配快照和 step 摘要，不启动真实 MCP Server，不执行 MCP Client 调用，也不做审批 UI。后续问数 Agent 通过 MCP 取数应在此基础上接入执行器和权限策略。

## 10. Knowledge Base 配置

当前知识库是配置和展示层，不是真实索引层。

配置来源：

- 内置默认集合
- 本地 `moyu.config.json` 的 `knowledge_bases`

支持字段：

- `title`
- `state`
- `embedding_role`
- `chunk_strategy`
- `connected_agents`
- `sources`
- `write_back.enabled`
- `write_back.policy`
- `write_back.allowed_artifact_types`

Workbench Settings -> Knowledge 会展示这些配置。

## 11. Artifact Write-Back

Artifact write-back 是“审核后的产物允许回流知识库”的记录，不是向量索引。

CLI：

```bash
npm run dev -- artifact write-back <artifact_id> \
  --collection <collection_id> \
  --reviewer <name>

npm run dev -- artifact write-backs
```

记录包含：

- source artifact
- target collection
- reviewer
- review note
- reviewedAt
- artifact hash 和路径快照

当前会校验：

- collection 是否存在
- write-back 是否启用
- artifact type 是否允许

## 12. Workbench 数据聚合

`buildWorkbenchData` 聚合：

- selected run
- works
- messages
- artifacts
- agents
- settings

输出给：

- `GET /api/workbench`
- `npm run workbench:export-data`
- 静态 `ui/workbench/public/data/workbench.json`

## 13. 沙箱状态

当前没有实现沙箱执行。所有 CLI 和 Workbench API 都在本地 Node 进程内执行。

后续沙箱设计方向：

- L0：可信内置逻辑，同进程执行
- L1：受控 Skill 使用 worker_threads / isolated-vm
- L2：高风险工具或外部依赖使用 Docker

在 L1 / L2 未实现前，不允许把任意生成代码描述为可安全执行。

## 14. 当前限制

- Trace 是 JSON 文件，不支持并发写数据库事务
- WorkStore 是单 JSON 文件，不适合长期大量会话
- Artifact path 是本机绝对路径，跨机器迁移需要导出机制
- 没有暂停、续跑、取消和重试调度器
- 没有通用 DAG / ReAct workflow engine
- 没有真实知识库索引和召回
- 没有 sandbox 隔离

这些限制要在用户可见 UI 或文档中明确，不做静默承诺。
